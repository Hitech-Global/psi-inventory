## 一、当前汇率来源事实（只读核查结果）

### 1.1 表结构 exchange_rates（db.js:211-221）

```
id           TEXT PRIMARY KEY
from_currency TEXT NOT NULL
to_currency   TEXT NOT NULL
rate          REAL NOT NULL
rate_date     TEXT NOT NULL
rate_type     TEXT DEFAULT 'realtime'
created_at    TEXT DEFAULT (datetime('now'))
```

- **唯一索引仅有 PK（sqlite_autoindex on id）**；`(from_currency,to_currency,rate_date,rate_type)` 无任何唯一约束。
- **无 rate_source 列**；**无 is_manual/confirmed_by 列**；**无 status 列**；**无版本列**。→ 数据库层无法区分自动行情与人工确认，无法记录来源，无法多候选并存管理。

### 1.2 现存数据（全表 1 行）

| id | from | to | rate | rate_date | rate_type |
|---|---|---|---|---|---|
| rate_1783231833480_9zdr2z | IDR | RMB | 0.000377 | 2026-07-05 | realtime |

- 全表**仅 1 行**，方向为 **IDR→RMB**（1 印尼盾 = 0.000377 人民币）。
- rate_type 仅有 `realtime` 一种。

### 1.3 币种与国家主数据

- currencies（active）：USD、RMB、IDR、MYR、THB。**注意：无任何一条 is_base=1**（系统未在数据层声明本位币）。
- countries.default_currency：印度尼西亚→IDR、马来西亚→MYR、泰国→THB（与 A5 一致）。

→ 成本原币主要为 **USD**，少量 RMB；目标本币为 **IDR/MYR/THB**。

### 1.5 汇率刷新来源（server.js）

| 项 | 事实 |

## 二、当前支持能力（能做什么）

1. 从免费 API 拉取「今日」CNY→外币行情，倒数后按「外币→RMB / realtime」缓存。
2. `POST /api/exchange-rates` 手工插入任意方向/日期/类型的一条汇率。
3. `/latest` 查询：正向优先，无正向时自动取反向倒数。
4. 展示层做 6 位小数舍入换算（1 人民币 = X 外币）。

## 四、汇率候选记录 与 最终采用事实 的边界（本轮核心）

严格区分三层，**不得混淆**：

### A. 汇率生效键（Effective Key）
逻辑判定用键，至少包含：
```
(source_currency, target_currency, rate_date, rate_type)
```

### B. 汇率候选记录（Candidate）
同一生效键下，可能因 `rate_source` / 自动或人工 / 数据版本 / 汇率值 / 状态 不同而**并存多条**。候选层允许多条——这是行情事实的自然形态。

### C. 最终采用事实（Applied Fact）
成本确认时，从候选中**选择一条**，或经**倒数 / 受控交叉**计算出唯一 `applied_rate`，连同完整组成路径生成**不可变快照**（P1-WAC-04 方案 B 的 `exchange_rate_snapshot`）。

> **关键澄清（承接 A10）**：「生效键唯一」是**采用事实层**（一次成本确认只锁定一个 applied_rate）的语义，**不得**错误理解为「行情表物理上每生效键只能有一条记录」。是否给 exchange_rates 加唯一键，留待 P1-WAC-05 规则冻结后、由后续实施任务另行裁断——本轮不决定、不执行。

## 五、直接汇率规则（冻结）

1. **直接汇率优先级最高**：给定 (source, target, rate_date, rate_type)，若存在 from=source & to=target & 同 rate_date & 同 rate_type 的候选，则**必须优先使用直接汇率**，不得改用倒数或交叉。
2. **原始方向即使用方向**：直接汇率的 `applied_rate = 候选 rate`，方向 source→target，无需变换。
3. 直接汇率命中时，倒数汇率、交叉汇率**一律不参与**（即使它们同时存在）。
4. rate_date 必须与请求锚点日期**精确一致**（A1=CI 出货日、A2=各次付款完成日），**禁止**用相邻日期/最新日期近似替代（近似替代属另案，非本轮授权）。
5. rate_type 必须与成本用途一致（成本用途不得取 realtime，见规则十五-15）。

## 六、倒数汇率规则（冻结）

1. **允许条件（全部满足）**：① 同生效键**无直接汇率**候选；② 存在**反向**候选（from=target & to=source & 同 rate_date & 同 rate_type）；③ 反向 rate > 0。
2. **计算**：`applied_rate = 1 / reverse_rate`。
3. **精度与舍入**：倒数计算**保留高精度中间值**（不早舍入）；最终 applied_rate 与 CI 货物成本换算精度对齐（建议统一 8 位小数、四舍五入，具体舍入位数与规则并入 P1-WAC-06 精度设计，本轮只冻结「先算后舍、不早舍、可复算」原则）。
4. **快照留证**：倒数得到的 applied_rate 必须在快照中记录：`is_reciprocal=1`、原始 reverse 候选标识、原始 reverse rate、方向说明，保证可独立复算。
5. 直盘存在时**禁止**使用倒数（承接规则五-3）。

## 七、交叉汇率规则（冻结）

1. **触发条件**：同生效键**既无直接、也无可用倒数**时，方可考虑交叉。
2. **仅允许受控桥接，禁止任意最短路径搜索**：不得让系统自动在币种图中搜索任意路径。
3. **允许的桥接币种候选（白名单，冻结）**：`{ USD, RMB }`。理由——成本原币事实为 USD（主）与 RMB（次），二者为业务天然枢纽币；IDR/MYR/THB 之间不互为桥接，绝不允许经第三国本币桥接。
4. **桥接选择优先级（冻结）**：① USD 优先；② RMB 次之。（因成本原币以 USD 为主，USD 桥接段更易有真实行情、精度损失更可控。）
5. **每段约束（全部强制）**：
   - 9-a：交叉每一段的 `rate_date` **必须一致**（均等于请求锚点日期）；
   - 10-a：交叉每一段的 `rate_type` **必须一致**（均为成本用途类型，不得混 realtime）；
   - 11-a：交叉各段的 `rate_source` **不允许混合**（两段必须同源，禁止「A 源 USD→X + B 源 X→本币」拼接）。
6. **最多两段**：source→bridge→target，**不允许三段及以上**。
7. **完整路径留证**：交叉快照必须记录每一段的候选标识、rate、rate_date、rate_type、rate_source 及最终合成 applied_rate，`is_cross=1`，保证逐段可复算。
8. 直盘/倒数存在时**禁止**交叉（承接规则五、六）。

## 八、同币种 rate=1 规则（冻结）

1. `source_currency == target_currency` 时，`applied_rate = 1`，**不查询行情表、不生成对外部行情的依赖**。
2. 同币种情形仍需生成快照事实（记录 `applied_rate=1`、`same_currency=1`）以保证审计链完整与复用判定一致，但该快照不引用任何行情候选。
3. 例：CI 货物成本 USD、目标本币若为 USD（当前范围内不存在，因本币仅 IDR/MYR/THB），保留规则以防未来币种扩展。

## 九、多来源候选选择规则（冻结）

同一天、同币种对、同 rate_type 存在多条候选时，**按固定优先级择一，禁止静默取最大/最新/任意**：

1. **人工确认候选 > 自动行情候选**（人工确认唯一时直接采用）。
2. 若存在**多条人工确认**且值不一致 → **阻断**，要求人工唯一化裁定（不得自动挑选）。
3. 若无人工确认、存在多条自动候选：
   - 3-a：若来自**指定权威来源**（rate_source 白名单，具体权威源清单并入实施任务）→ 取权威源；
   - 3-b：若无权威源标识或多源冲突且差异超阈值 → **阻断**，要求人工确认；
   - 3-c：**任何情况下不得**以「rate 值最大 / created_at 最新 / 随机」作为自动择优依据。
4. 依赖 rate_source / is_manual 的规则 2–3 需要 G1/G2 补齐后方可落地——本轮**只冻结规则**，实现属后续任务。

## 十、人工确认规则（冻结）

1. **人工确认可覆盖自动候选**：对同一生效键，人工确认值优先于自动行情，用于**新快照**的采用来源（承接规则九-1）。
2. **人工确认不得覆盖历史快照**：已锁定快照不可变（A6）。人工确认仅影响**尚未生成 / 后续新生成**的快照，**绝不回写、绝不改写**任何既有锁定快照。
3. **同一天重新确认时的复用**：若「完整事实」（生效键 + applied_rate + rate_source + 方向/倒数/交叉组成 + 精度）与既有快照**完全一致** → **复用**该快照（A7）；若任一要素不同 → 生成**新的不可变快照**，旧快照保留，**禁止覆盖**。
4. 人工确认动作须留审计（谁、何时、原值、新值），依赖 G1/G2 补齐。

## 十一、缺失及异常汇率阻断（冻结）

1. **缺汇率阻断**：给定生效键，直盘 / 倒数 / 受控交叉均无法得到 applied_rate 时 → **阻断**当前成本确认，返回明确错误（建议固定错误码如 `MISSING_COST_RATE`，含 source/target/rate_date/rate_type），**不得静默跳过、不得置 0、不得置 1**。
2. **异常值阻断**：`rate=0`、`rate<0`、`NaN`、`null`、或数量级异常（超出该币种对合理区间的上下界阈值）→ **阻断**，不得使用（异常量级阈值具体取值并入 P1-WAC-06 / 实施任务）。
3. **付款未完成阻断**（承接 A3）：其他费用未全部付款完成 → 阻断 Cost Confirm；CI 货物成本按出货日汇率，不受付款状态影响（例外）。
4. **严禁 realtime 静默兜底**（规则十五-15 的强制表述）：成本汇率缺失时**绝不允许**回退使用 realtime 行情充数——必须阻断。

## 十三、方案 A / B 比较

### 方案 A —— 严格直盘优先（含受控倒数，禁交叉）
- 直接汇率 → 无直盘则受控倒数 → 仍无则**阻断**；**不支持交叉**。

### 方案 B —— 受控交叉汇率
- 直接汇率 → 倒数 → 无直盘/倒数时允许**受控桥接**（白名单 USD/RMB，禁任意路径，保存完整路径）→ 仍无则阻断。

| 维度 | 方案 A 严格直盘 | 方案 B 受控交叉 |
|---|---|---|
| 数据覆盖率 | 依赖直盘/反向录入；当前需要的直盘对**仅 6 个**（USD/RMB × IDR/MYR/THB），可完整维护，覆盖率**可达 100%** | 更高，缺直盘时可经 USD/RMB 桥接补足 |
| 实施复杂度 | **低**（无多段合成、无路径逻辑） | 中（需两段校验、同日/同类型/同源约束、路径留证） |
| 审计能力 | **最强**（单段可直读，无合成歧义） | 强但更重（需逐段复算，路径证据更多） |
| 精度风险 | **最低**（至多一次倒数） | 较高（两段相乘 + 可能两次倒数，累积舍入） |
| 对当前币种适用性 | **高**——目标仅 3 本币、原币仅 USD/RMB，直盘对数量极少，人工维护即可覆盖 | 适用，但当前无需即可覆盖，交叉能力暂属冗余 |
| 是否二次返工 | **无返工**：A 是 B 的真子集，未来币种扩展时可平滑升级为 B，不破坏已锁定快照 | 若现在启用交叉，当前无真实需求，反而先引入精度/审计负担 |

## 十四、推荐方案

**推荐方案 A（严格直盘优先，含受控倒数，本阶段禁用交叉）作为成本汇率的冻结规则。**

理由：
1. **覆盖率已足够**：当前成本原币仅 USD/RMB，目标本币仅 IDR/MYR/THB，需要的直盘对**只有 6 个**，人工/行情维护即可 100% 覆盖，无需交叉。
