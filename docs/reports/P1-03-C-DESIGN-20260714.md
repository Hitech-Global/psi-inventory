## 1. CI 一对多 WAC 关系模型

### 1.1 正式关系（冻结）

```
一个 commercial_invoices（CI）
  └─ N 个 commercial_invoice_items（SKU 行）
       └─ 每个 (SKU + 国家 + 仓库) 维度
            └─ 恰好一条 wac_history 版本记录
```

- **权威关联**：`wac_history.ci_id` → `commercial_invoices.id`（一对多）。
- **查询整个 CI 的全部 WAC 版本**的唯一正式路径：
  ```sql
  SELECT * FROM wac_history WHERE ci_id = ? ORDER BY sku_code, country, warehouse, version_no;
  ```
- **禁止**以 `commercial_invoices.wac_version_id` 作为一对多版本关联。该字段为遗留单值指针，语义上只能指向单个版本，无法表达 N 个 SKU 的关系。

### 1.2 当前实现的问题（来自补充核验）

- `update-weighted-avg` 路由（server.js:4891）写 `wac_version_id = logs[0].wac_id`，即**仅关联第一个 SKU（SKU-001）的 WAC 记录**。
- 第二个 SKU（SKU-002）的 WAC 记录在 `wac_history.ci_id` 中正确关联，但 CI 头表无直接体现。
- 前端若以 `wac_version_id` 非空判定"CI 已确认"，只能说明"第一个 SKU 有版本"，会**遗漏其余 SKU**。

## 2. wac_confirmed 汇总状态规则

### 2.1 新增字段（commercial_invoices，幂等 migration）

| 字段 | 类型 | 默认 | 语义 |
|------|------|------|------|
| `wac_confirmed` | INTEGER | 0 | 整个 CI 的全部应参与 SKU 是否已生成 WAC 版本（0/1） |
| `wac_confirmed_at` | TEXT | '' | 汇总确认时间（datetime） |
| `wac_confirmed_by` | TEXT | '' | 汇总确认人 id |

### 2.2 状态语义

- `wac_confirmed = 1`：**仅当**本 CI 下"全部应参与计算的 SKU"都在同一个原子事务内成功生成了 locked+confirmed 的 WAC 版本后，才置 1。
- `wac_confirmed = 0`：初始值；或任一 SKU 版本生成失败导致整个事务回滚后保持 0。
- **禁止**以"存在任意一条 wac_history"即判定整个 CI 已确认（见第 3 节判定规则）。
- `wac_confirmed` 与既有 `cost_confirmed`（费用确认）、`cost_allocated`（费用分摊）是相互独立的三道闸门，互不替代。

### 2.3 前端判定"整个 CI 已确认"

- 前端读取 cost-summary 返回的 `wac_confirmed` 布尔值作为"CI 已完成 WAC 确认"的唯一依据。
- 前端展示"该 CI 下的 WAC 版本列表"时，调用 `GET /api/wac-history?ci_id=<ci_id>`，按 `wac_history.ci_id` 一对多展示，**不再依赖 `wac_version_id`**。
- 成本确认按钮的"已确认"禁用态，由 `wac_confirmed === 1` 控制（替代当前的 `wac_version_id` 非空）。

## 3. "全部 SKU 已成功生成版本"判定规则

### 3.1 应参与计算的 SKU 集合定义

WAC 版本由 `update-weighted-avg` 路由逐 `cost_allocations` 行生成。因此：

- **期望版本数 `expectedCount`** = 本 CI 的 `cost_allocations` 行数（`SELECT COUNT(*) FROM cost_allocations WHERE ci_id = ?`）。
- **实际版本数 `actualCount`** = 本事务内成功插入的 `wac_history` 行数（`logs.length`）。

> 备注（已知限制，非本轮修复）：当前路由通过 `original_inventory_imports.find(sku_code)` 取国家/仓库，同一 SKU 多国家/仓库时只取第一条。若未来需要同一 SKU 多国家各一条版本，应在 `cost_allocations` 增加 country/warehouse 列或改以 `original_inventory_imports` 的 (sku,country,warehouse) 去重集合为期望集。本轮维持现有迭代集合（`cost_allocations` 行数），但在事务内增加"缺失 origInv 即抛错"的强校验（见 3.3）。

### 3.2 汇总确认判定（事务内）

在 `transaction(() => { ... })` 末尾、提交前：

```
IF actualCount === expectedCount AND expectedCount > 0:
    SET wac_confirmed = 1, wac_confirmed_at = now, wac_confirmed_by = currentUserId
ELSE:
    THROW  'WAC 版本数量与应参与 SKU 数量不一致，已回滚'   // 触发整体回滚
```

此规则确保：**只有全部 SKU 都成功，才允许 `wac_confirmed=1`**；任一 SKU 失败 → 抛错 → 事务整体回滚 → `wac_confirmed` 保持 0。

### 3.3 缺失 original_inventory_imports 的处理（完整性补强）

当前路由对缺失 `origInv` 的行执行 `if (!origInv) return;`（静默跳过），会导致 `actualCount < expectedCount` 却被误标成功。

**P1-03-C 修正**：将静默跳过改为**抛错**：

```js
const origInv = importedSkus.find(s => s.sku_code === alloc.sku_code);
if (!origInv) {
  throw new Error(`SKU ${alloc.sku_code} 缺少原库存导入记录，无法生成 WAC 版本`);
}
```

这样缺失即触发整体回滚，杜绝"部分 SKU 版本 + wac_confirmed 误置 1"。

## 5. UPDATE / DELETE 触发器设计

### 5.1 目标

为 `wac_history` 增加数据库层不可变保护，填补补充核验发现的"仅有 is_locked 标记 + UNIQUE 索引，无真正防 UPDATE/DELETE 保护"的缺口。

### 5.2 触发器 1：BEFORE UPDATE（阻止修改已锁定记录）

```sql
CREATE TRIGGER IF NOT EXISTS trg_wac_history_block_update
BEFORE UPDATE ON wac_history
WHEN OLD.is_locked = 1
BEGIN
  SELECT RAISE(ABORT, '锁定版本的加权平均成本历史记录不可修改 (id=' || OLD.id || ', version_no=' || OLD.version_no || ', sku=' || OLD.sku_code || ')');
END;
```

### 5.3 触发器 2：BEFORE DELETE（阻止删除已锁定记录）

```sql
CREATE TRIGGER IF NOT EXISTS trg_wac_history_block_delete
BEFORE DELETE ON wac_history
WHEN OLD.is_locked = 1
BEGIN
  SELECT RAISE(ABORT, '锁定版本的加权平均成本历史记录不可删除 (id=' || OLD.id || ', version_no=' || OLD.version_no || ', sku=' || OLD.sku_code || ')');
END;
```

### 5.4 设计要点

- `WHEN OLD.is_locked = 1` 仅对锁定记录生效；未锁定记录（如未来调整/冲销草稿）仍可正常 UPDATE/DELETE。
- `RAISE(ABORT, ...)` 中止整个语句并回滚当前事务，错误信息含记录标识，便于定位。
- 触发器对所有列生效（见第 6 节核心字段清单），因当前 `wac_history` 全部 26 列均为业务核心字段，无纯技术字段。
- 幂等：`CREATE TRIGGER IF NOT EXISTS`，重复执行不报错。

## 6. locked 核心不可修改字段清单

`wac_history` 当前 26 列**全部为核心业务字段**，锁定后均不可修改：

| # | 字段 | # | 字段 |
|---|------|---|------|
| 1 | id (PK) | 14 | original_qty |
| 2 | version_no | 15 | original_avg_cost |
| 3 | ci_id | 16 | original_inventory_value |
| 4 | ci_no | 17 | inbound_qty |
| 5 | po_id | 18 | unit_landing_cost |
| 6 | po_no | 19 | inbound_total_cost |
| 7 | pi_id | 20 | new_avg_cost |
| 8 | pi_no | 21 | settlement_date |
| 9 | sku_code | 22 | confirmation_status |
| 10 | model | 23 | is_locked |
| 11 | brand | 24 | confirmed_by |
| 12 | country | 25 | confirmed_at |
| 13 | warehouse | 26 | created_at |

**纯技术字段**：当前**不存在**。若未来新增纯技术字段（如 `audit_note`、`updated_at`、`sync_flag`），应：
1. 在触发器 `WHEN` 之外增加列级判断，仅当核心字段被改动时才 `RAISE`；或
2. 将触发器改为"仅当核心字段 NEW/OLD 不一致时中止"，允许技术字段更新。
本轮不新增技术字段，触发器按"锁定即全禁止 UPDATE"实现。

## 7. migration 方案（db.js，幂等）

```js
// P1-03-C: CI WAC 汇总状态字段
['wac_confirmed INTEGER DEFAULT 0',
 'wac_confirmed_at TEXT DEFAULT \'\'',
 'wac_confirmed_by TEXT DEFAULT \'\''].forEach(col => {
  try { d.exec(`ALTER TABLE commercial_invoices ADD COLUMN ${col}`); } catch(e) {}
});

// P1-03-C: locked WAC 版本数据库层不可变保护
try {
  d.exec(`CREATE TRIGGER IF NOT EXISTS trg_wac_history_block_update
    BEFORE UPDATE ON wac_history
    WHEN OLD.is_locked = 1
    BEGIN
      SELECT RAISE(ABORT, '锁定版本的加权平均成本历史记录不可修改 (id=' || OLD.id || ', version_no=' || OLD.version_no || ', sku=' || OLD.sku_code || ')');
    END;`);
} catch(e) {}
try {
  d.exec(`CREATE TRIGGER IF NOT EXISTS trg_wac_history_block_delete
    BEFORE DELETE ON wac_history
    WHEN OLD.is_locked = 1
    BEGIN
      SELECT RAISE(ABORT, '锁定版本的加权平均成本历史记录不可删除 (id=' || OLD.id || ', version_no=' || OLD.version_no || ', sku=' || OLD.sku_code || ')');
    END;`);
} catch(e) {}
```

**幂等性**：`ALTER TABLE ... ADD COLUMN` 与 `CREATE TRIGGER IF NOT EXISTS` 均包裹 try/catch，重复执行安全；重启不会重复建列或报错。

**不回填**：不读取/不写入任何历史 `wac_history` 记录；不修改 `wac_version_id` 既有值。

## 8. Test 9 设计：多 SKU CI 中途失败整体回滚

### 8.1 目标

验证一个含 ≥2 SKU 的 CI，在事务中第二个 SKU 失败时，第一个 SKU 的 WAC 版本、cost_allocations、cost_update_logs、CI 汇总状态、inventory、skus **全部回滚/不变化**。

### 8.2 测试数据

- 新建独立 CI（前缀 `P103C-TEST-CI-`）。
- 2 个 SKU（`P103C-TEST-SKU-001` / `-002`），各自 `commercial_invoice_items` + `original_inventory_imports`（含 country/warehouse）+ `cost_allocations`（已 cost_allocated）。
- CI 前置：`cost_confirmed=1`、`cost_allocated=1`、`original_inventory_imported=1`。

### 8.3 失败注入机制（测试侧，不改应用代码）

当前 `generateWacVersion` 用 `genId('wac')` 生成主键，且 `version_no = MAX+1` 逻辑对版本号天然防碰撞。为**确定性**触发事务内抛错，采用测试侧 stub：

- 测试在调用路由前，**临时 stub `genId`**（或等价 ID 生成函数），使第二个 WAC 插入复用已预置的 `wac_history.id`：
  - 预置一条 `wac_history` 记录，`id = 'wac_FORCED_FAIL_P103C'`，`is_locked = 0`（未锁定，避免被触发器拦截），其余字段任意合法值。
  - stub 使 `generateWacVersion` 对**第二个 SKU** 返回 `id = 'wac_FORCED_FAIL_P103C'`。
  - 路由第二个 SKU 的 INSERT 触发 **PRIMARY KEY 冲突** → 抛出 → 事务整体回滚。
- stub 在测试结束后还原。
- **不修改任何应用代码**；stub 仅存在于测试进程内存。

> 备选注入（若 genId 不可 stub）：在第二个 SKU 的 `original_inventory_imports` 故意制造约束冲突（如使 `generateWacVersion` 插入触发 NOT NULL）。但 PK stub 最简洁、最确定，优先采用。

### 8.4 验证断言（全部须成立）

| # | 断言 | 期望 |
|---|------|------|
| 9.1 | 路由返回错误（500 或明确错误），非成功 | 失败 |

## 11. 回滚方案

若 P1-03-C 实施后发现需回退：

1. **触发器回滚**（数据库层）：
   ```sql
   DROP TRIGGER IF EXISTS trg_wac_history_block_update;
   DROP TRIGGER IF EXISTS trg_wac_history_block_delete;
   ```

   - 若 SQLite ≥ 3.35（当前满足）：`ALTER TABLE commercial_invoices DROP COLUMN wac_confirmed;`（及 `_at`/`_by`）。

3. **代码回滚**：`git revert` 或手工还原 server.js/app.js 中第 9 节所列改动。
4. **wac_version_id**：全程未动，无需回滚。
5. 回滚后不影响 P1-03-B 已生成的 `wac_history` 数据（触发器删除后仍可读；字段保留不影响查询）。
