# 方案：采购单据（PO / PI / CI·PL）删除与作废能力（最小范围 · 测试单清理优先）

> 目标：在继续测 PO / PI / CI / PL 之前，先补上"清理测试单"的能力，避免系统里越堆越多。
> 原则（用户明确）：不做"所有单据都可硬删除"；优先支持测试单清理；不扩大到复杂历史单据。
> 范围：仅出方案，未改代码。

> **状态：已收口（2026-07-11 18:15）** — 后端作废/删除能力已落地并端到端验证通过；用户确认本轮通过，前端按钮待定。详见文末「6. 实施记录」。

---

## 0. TL;DR（推荐最小切法）

- **主路径用「软作废」**：把单据状态置 `cancelled`。`updateInventoryTransitData()` 三处聚合**本来就排除 `cancelled`**（server.js:949 / 968 / 986），作废后重算 transit 自动回落，**零级联风险、零新增聚合逻辑**。
- **仅 PO 增加「硬删除」**：且限定 `draft` 或"无活跃 PI 的 transferred_pi"——这是订单预测"生成PO"产生的测试单主形态，删后调 `updateInventoryTransitData()` 回落。
- **PI / CI 本轮不做硬删除**：因为建 PI 会把 PO 翻成 `transferred_pi`、建 CI 会把 PI 翻成 `shipped_complete` 并改写 PI 明细 `shipped_qty`/金额——硬删需要级联回退这些状态与字段，属"复杂历史单据"，留后续。
- **`available_qty` 不受影响**：作废/删除的都是未入库单据（CI `completed`/`partial_inbound` 不允许作废），`inbound` 才动 `available_qty`，与作废无关。

## 1. 当前系统现状（只读核对）

| 单据 | 已有删除/作废能力 | 现状说明 |
|---|---|---|
| **PO** | 有硬删 `DELETE /api/purchase-orders/:id`（server.js:2585） | **无状态守卫**（任何状态都能删）；**删后不调 `updateInventoryTransitData()`** → `po_unconfirmed_pi_qty` 不回落（残留旧值）。无作废/取消端点。状态机含 `cancelled` 但无入口设置它。前端 PO 列表无删除按钮。 |
| **PI** | **无**删除、**无**作废端点 | 仅 create / edit / attachment / batch-import。状态含 `cancelled`，且前端 PI 筛选下拉**已有「已取消」选项**（app.js:4347）——说明 `cancelled` 是预期状态，只是没入口。 |
| **CI / PL** | **无**删除、**无**作废端点 | CI 仅 create / attachment；PL 是 CI 子表（`packing_lists` + `packing_list_items`，`related_ci_id`），无单独删除端点。建 CI 会把关联 PI 翻成 `shipped_complete`/`partial_shipped` 并改写 PI 明细 `shipped_qty` 与金额/定金字段（server.js:2873-2883）。 |
| 先例 | outbound_records 已有软作废模式 | `status='voided'` + `POST /api/outbound-records/batch-void` + 作废原因 + 操作日志（server.js:4672+）。作废不改库存（已入库的不在此列），可参照其"原因必填 + 留痕"做法。 |

**结论**：系统目前对 PO/PI/CI 几乎没有任何安全的清理出口；唯一的 PO 硬删还"删不干净"（transit 不回落）。这正是每轮测试都会留垃圾的根因。

## 2. 各状态允许的操作（建议规则）

> 标注：✓硬删 = 允许硬删除；✓作废 = 允许软作废；✗ = 禁止。

### PO（`po_status`）
| 状态 | 硬删 | 作废 | 说明 |
|---|---|---|---|
| draft | ✓ | ✓ | 测试单主形态（订单预测"生成PO"产出 draft），无下游，硬删安全 |
| pending_approval / approved / sent_factory / rejected | ✗ | ✓ | 未转 PI，可作废；硬删禁止（避免误删已审批单） |
| transferred_pi / partial_pi | ✗* | ✓ | 已转 PI；*仅当"该 PO 无活跃(非cancelled) PI"时可硬删（见 §5.2 守卫）；否则先作废其 PI。作废 PO 本身无需管 PI |
| completed | — | — | PO 无此态 |

### PI（`pi_status`）
| 状态 | 硬删 | 作废 | 说明 |
|---|---|---|---|
| pending / uploaded / confirmed / pending_deposit / deposit_paid / producing / pending_ci_pl | ✗(本轮) | ✓ | 测试 PI 多停在这些态，作废即可清理 |
| shipped_complete / partial_shipped | ✗ | ✓ | 其 CI 需另行作废；PI 作废不影响 transit（CI 才是 in_transit 来源） |
| completed | ✗ | ✗ | 已完结，保留 |

### CI（`ci_status`）
| 状态 | 硬删 | 作废 | 说明 |
|---|---|---|---|
| draft / uploaded / ci_pl_uploaded | ✗(本轮) | ✓ | 测试 CI 多停在这些态 |
| partial_inbound / completed | ✗ | ✗ | 已发货/入库，保留；如需撤销走业务冲销（非本轮） |

### PL
- 作为 CI 子表，**随 CI 作废/删除级联**（仅元数据，不影响 transit）。本轮不单独立端点。

## 3. 删除/作废后需要联动回写的字段

| 字段 | 触发 | 回写方式 |
|---|---|---|
| `po_unconfirmed_pi_qty` | 删/作废 **PO** | `updateInventoryTransitData()` 重算（PO 聚合 `NOT IN ('cancelled','transferred_pi')`）→ 自动回落 |
| `pi_confirmed_unshipped_qty` | 删/作废 **PI** | 同上（PI 聚合 `NOT IN ('cancelled','completed')`）→ 自动回落 |
| `in_transit_qty` | 删/作废 **CI**（级联 PL） | 同上（CI 聚合 `NOT IN ('cancelled')`）→ 自动回落 |
| `available_qty` | — | **不受影响**（作废/删除的都是未入库单据；`inbound` 才动 available，且 available 自动回写本轮仍禁用、来自导入覆盖） |

**关键点**：全部复用已有的 `updateInventoryTransitData()`，**不新写聚合 SQL**，保证与阶段A（自动回写）、方案B（订单预测实时列）完全一致，不会带坏已接好的实时链路。

---

## 4. 如何保证不破坏已接好的实时回写 / 预测实时字段

1. **阶段A**：`updateInventoryTransitData()` 在 PO/PI/CI 创建时已被调用（CI 创建末尾 server.js:2886）。删除/作废端点**收尾同样调用它** → `inventory` 三字段按"现存活跃单据"重算，被删/作废单据自然不再计入 → 自动回落。
2. **方案B**：订单预测页 4 列（PO未确认PI / PI已确认未发货 / 在途 / 总库存池）直接读 `inventory` 实时值。inventory 回落 → 页面**无需手动重新计算**即同步。
3. **作废用 `status='cancelled'`**，恰是 `updateInventoryTransitData` 三处聚合的排除值（server.js:949/968/986 都是 `NOT IN ('cancelled',...)`）→ 与现有逻辑天然一致，**零新增分支**。
4. **验证方法**：作废一张测试 PO/PI/CI 后，不点重新计算，直接看订单预测页对应列回落。
5. **风险隔离**：作废不改 `available_qty`、不改 `generate`、不改三页口径 / 三周转 / 停采 / 失真 / 多维周转 / 自动重算挂载 / 采购链状态机。仅"把 cancelled 单据排除出 transit 聚合"——这本就是设计意图（聚合 SQL 早已这样写）。

## 5. 最小实施方案（本轮范围）

### 5.1 后端 — 统一软作废端点（三类型复用同一 handler 逻辑，分三条路由）
- `POST /api/purchase-orders/:id/void`
- `POST /api/proforma-invoices/:id/void`
- `POST /api/commercial-invoices/:id/void`
- 权限：`po_create` / `pi_edit` / `ci_edit`（按既有端点习惯，可微调）
- 入参：`{ void_reason }`（必填；写入 `cancel_reason` + `cancelled_at`，见 5.3）
- 逻辑：
  - **PO**：`po_status` 置 `'cancelled'`（所有状态都允许作废）。
  - **PI**：若 `pi_status='completed'` → `400` 拒绝；否则置 `'cancelled'`。
  - **CI**：若 `ci_status='completed'` → `400` 拒绝；否则置 `'cancelled'`（其 PL 保留，不影响 transit）。
  - 收尾：调用 `updateInventoryTransitData()`（三端点各自调一次即可）。
- 已知限制（可接受，测试清理场景）：作废 CI **不回退** PI 的 `shipped_qty`/金额/定金字段（这些是 PI 内部财务字段，非 transit）；完整财务回退留后续。

### 5.2 后端 — 改造现有 PO 硬删 `DELETE /api/purchase-orders/:id`
- 加守卫：仅当 `po_status='draft' OR (po_status IN ('transferred_pi','partial_pi') AND 该 PO 无活跃(非cancelled) PI)` 才允许；否则 `400 "该 PO 仍有活跃 PI，请先作废 PI"`。
- 删后调用 `updateInventoryTransitData()` 回落 `po_unconfirmed_pi_qty`。
- **PI / CI 硬删本轮不做**（理由见 §2 / §4 风险）。

### 5.3 后端 —（可选，低优先）schema
- 三表加可空列 `cancel_reason TEXT`、`cancelled_at TEXT`（幂等 ALTER，类似此前三分量列）。
- 若不想动 schema：作废原因 append 到 `remark` 字段即可。推荐加列以保留审计痕迹。

### 5.4 前端
- **作废按钮**：PO/PI/CI 列表与详情增加「作废」按钮；按状态禁用（`completed`/已入库态不可作废；PI/CI 在 draft/uploaded 等可点）。点击弹确认框 + **作废原因输入（必填）** → 调 void 端点 → 刷新列表。
- **删除按钮（仅 PO）**：PO 列表增加「删除」按钮（仅 `draft` 或无活跃 PI 时可用）→ 二次确认（"此操作不可逆，将同步回落在途字段"）→ 调 `DELETE` 端点。
- **状态标签**：前端为 `cancelled` 增加中文"已取消/已作废"徽章（PO 当前直接英文显示；PI 筛选已有 cancelled 选项，列表状态列补中文更佳）。
- **权限**：作废/删除按钮受 `hasPermission` 控制（`po_create` / `pi_edit` / `ci_edit`）。

### 明确不做（本轮）
- PI/CI 硬删除（需级联回退 PO/PI 状态与 PI 明细 `shipped_qty`/金额，属复杂历史单据）。
- 作废后的财务字段回退（PI `shipped_qty`/金额、定金抵扣等）。
- 多级联作废（作废 PO 不自动级联作废其 PI/CI；用户按链反向逐张作废，符合"测试清理"手动操作习惯）。
- 不动 `available_qty` / `generate` / 三页口径 / 三周转 / 停采 / 失真 / 多维周转 / 自动重算挂载 / 采购链状态机。

## 6. 验证清单（开改后）
1. 建测试 PO(draft) → 订单预测页 `PO未确认PI` +X；**作废 PO** → 不点重算，页面对应列 -X，`inventory.po_unconfirmed_pi_qty` 回落。
2. 建 PI（翻转 PO→transferred_pi）→ **作废 PI** → `pi_confirmed_unshipped` 回落；PO 仍可正常作废。
3. 建 CI（翻转 PI→shipped）→ **作废 CI** → `in_transit` 回落；PL 保留。
4. **硬删** draft PO → `inventory.po_unconfirmed_pi_qty` 回落，无残留。
5. 不变量：三页口径 / 停采 / 失真 / 三周转 **0 变化**（与方案B验收同一批断言）。
6. 边界：completed PI/CI 作废被拒；有活跃 PI 的 PO 硬删被拒。

## 7. 与已落地能力的衔接
- 阶段A（3 在途字段自动回写）：本方案的作废/删除端点**复用并依赖** `updateInventoryTransitData()`，不另写聚合，衔接零摩擦。

## 8. 实施记录（已落地 · 2026-07-11）

### 8.1 实际改动（仅 server.js，前端本轮未改）
- 新增 3 个作废端点（均必填 `void_reason`，置 `cancelled`，收尾调 `updateInventoryTransitData()` + `logOperation` 留痕）：
  - `POST /api/purchase-orders/:id/void`（权限 `po_create`）
  - `POST /api/proforma-invoices/:id/void`（权限 `pi_edit`）：`completed` 拒绝
  - `POST /api/commercial-invoices/:id/void`（权限 `ci_edit`）：`completed` / `partial_inbound` 拒绝
  - 作废原因追加写入各表 `remark`（格式 `[作废 时间 by 操作人] 原因: xxx`），未新增 schema 列（保持最小）。
- 改造 `DELETE /api/purchase-orders/:id`：加守卫（仅 `draft`，或 `transferred_pi`/`partial_pi` 且无活跃 PI），删后调 `updateInventoryTransitData()` 回落；其余状态返回 400。

### 8.2 必要修正：updateInventoryTransitData 改为"全量清零后重算"
- **原问题**：该函数原实现只 `UPDATE` 聚合中出现的行；当某 SKU 贡献降为 0 时不产生聚合行 → 旧值残留，作废/删除后 transit 字段不回落（实测 PO 作废后仍显示 100）。
- **修正**：在三个聚合写入前各加一句 `UPDATE inventory SET <字段> = 0`（清零全部行），再按活跃单据聚合写入。现为真·全量重算（与函数注释"全量重算，幂等"一致）。
- **影响**：RDM724B=1752、总 PO未确认PI=8225 等既有正值**不变**；仅"应归零却残留"的行被纠正。三页口径/停采/失真/三周转零影响。

### 8.3 端到端验证（全部通过，未点重新计算）
- PO 作废：+100 → 0 ✓；PO 硬删(draft)：+50 → 0 ✓
- PI 作废：+200 → 0 ✓
- CI 作废（含 logistics_batch）：在途 +300 → 0 ✓
- 守卫：有活跃 PI 的 PO 硬删被拒(400) ✓
- 不变量：Σsuggested==Σ线上+Σ线下+Σ其他（违例0）；71 停采行 suggested 全 0；真实 PO(PO-2026-998922 → RDM724B=1752) 完好 ✓
- 测试单据全部清理（SQL 删 TEST-% + 触发重算），库干净。
