# 排查报告：总预测 vs 线上/线下「建议采购数量」不一致（差额 240）

> 只读排查，未改代码。结论：这是订单预测页面**三处「建议采购数量」用不同公式**导致的结构性不一致，**与采购链无关**（用户尚未做采购链操作，且采购链不触发重算）。

## 0. 用户现象（当前筛选视图）
- 总预测页「建议采购数量」合计 = 8194
- 线上页「建议采购数量」合计 = 7768
- 线下页「建议采购数量」合计 = 186
- 线上 + 线下 = 7954
- 差额 = 8194 − 7954 = **240**

用户质疑：这 240 是不是漏算了某个渠道 / 三页公式分叉。

## 1. 三处「建议采购数量」各自的真实公式

### (A) 总预测页「建议采购数量」列
- 列定义 key=`total_target_stock`（app.js:2281），但渲染值来自 `c.sq`（app.js:3081-3082），而 `c.sq = r.suggested_qty`（app.js:2979）。
- 底部合计 `totals.sq += c.sq`（app.js:3110）→ **合计 = Σ 后端 `suggested_qty` 列**。
- 后端 `suggested_qty` 落库逻辑（server.js:2224-2238, 2284, 2297）：
  ```
  if (blocked) suggested_qty = 0;
  else {
    online_allocated  = round(total_inventory_pool * online_pct);   // online_pct = 线上period月均 / 总period月均
    offline_allocated = round(total_inventory_pool * offline_pct);
    online_base  = max(0, online_target_stock  - online_allocated);
    offline_base = max(0, offline_target_stock - offline_allocated);
    suggested_qty = round(online_base + offline_base + other_target_stock);
  }
  moqQty = ceil(suggested_qty / qty_per_carton) * qty_per_carton;   // 箱规向上取整
  // 落库：suggested_qty 列 = ? , moq_qty 列 = moqQty , carton_adjusted_qty = moqQty
  ```
- **实测**：全库 Σ `suggested_qty` = Σ `moq_qty` = 24905，二者完全相等 → 说明 `suggested_qty` 列实际写入的是 **MOQ 取整后** 的值（即 = moqQty）。

### (B) 线上页「建议采购数量」
- 每行 `r._c.suggestedQty = (avgSalesPeriod>0 && !_block) ? Math.max(0, targetStock - allocatedStock) : 0`（app.js:3183）。
  - `targetStock = online_target_stock`，`allocatedStock = round(pool * pctPeriod/100)`，`pctPeriod = 线上period月均 / 总period月均`（app.js:3162-3169）。
- 底部合计 `totals.suggestedQty += Math.round(c.suggestedQty)`（app.js:3325）。
- **关键：此处没有 MOQ/箱规取整**，且拦截用 `shouldBlockReplenish(存储的 sales_status, risk_tags)`（app.js:2313）。

### (C) 线下页「建议采购数量」
- 同 (B)，只是 `targetStock = offline_target_stock`（app.js:3157）。

## 2. 理论上是否应满足 总预测 = 线上 + 线下？
**概念上应当相等**（每单位采购服务于线上/线下/其他之一），但**当前实现用两套不同公式**，因此不会严格相等：

| 维度 | 总预测页 (Σ suggested_qty) | 线上/线下页 (Σ 前端 suggestedQty) |
|---|---|---|
| 库存扣减 | 后端用 `total_inventory_pool` 按渠道占比分摊后减 | 前端用 `total_inventory_pool` 按渠道占比分摊后减（同一 pool、同一占比） |
| MOQ/箱规 | **有**（ceil 到整箱） | **无**（原始整数） |
| 拦截来源 | generate 时 `classifySkuState` 实时判定 | 前端按**存储**的 sales_status/risk_tags 判定 |
| other 渠道 | 计入（other_target_stock） | 不计入（只线上+线下） |

→ 只有在「MOQ=1 且 generate 与前端拦截完全一致且 other=0」时才偶然相等，否则必有差。

## 3. 这 240 到底来自哪里（用真实数据拆解）

### 全量数据实测（无筛选）
- Σ 总预测(suggested_qty, 含MOQ) = **24905**
- Σ 线上(前端, 无MOQ) = 23993；Σ 线下(前端, 无MOQ) = 1149 → 线上+线下 = **25142**
- 全量差额 = 24905 − 25142 = **−237**

### 差额的结构性来源（两部分）
1. **MOQ/箱规取整**：总预测页对每行做 `ceil(建议量/箱规)×箱规` 向上取整；线上/线下页用原始整数、不做取整。
   - 理论上 MOQ 使总预测**偏高**（向上取整）。
2. **后端分摊口径 vs 前端逐渠道分摊口径的取整差 + 拦截口径差**：
   - 后端是「先各自 max(0, 目标−分摊) 再求和」后整体取整；前端是「逐渠道单独 max(0,…) 后各自求和、不取整」。
   - 逐行对照发现 **30 行**「generate 时判定为拦截(suggested_qty=0)」但「按存储标签前端不拦截」，导致后端比前端少计约 660（全量）；这部分使后端**偏低**。
   - 二者方向相反，全量下净差 −237；**换一组筛选 SKU 时方向可翻转**（用户视图 +240，即 MOQ 向上取整在该子集占主导）。

### other_target_stock 是否贡献？
- 全量 Σ `other_target_stock` = **0** → **对差额 0 贡献**。即 240 不是「漏算其他渠道」。

### 结论
240 = **MOQ 取整贡献** + **后端/前端分摊与拦截口径差** 的累计；与采购链、与「漏算渠道」均无关。

## 4. 影响与建议（仅建议，未改）
- 现状：三页「建议采购数量」口径不一致，导致 总预测 ≠ 线上 + 线下，差额随筛选浮动（可正可负）。
- 若要三页严格可加，需统一为**单一公式**：推荐「总预测页也改为按渠道拆分求和（与线上/线下同源），并对齐 MOQ/拦截口径」，或「渠道页直接读后端 suggested_qty 的渠道分量」。
- 关联隐患：总预测页列 key 名为 `total_target_stock` 但实际渲染 `suggested_qty`（app.js:2281 与 2979），属命名误导，建议后续一并理顺。

## 5. 验证方法（可复现）
- 全量求和脚本：`/tmp/decompose2.js`、`/tmp/diag.js`（只读，复用 better-sqlite3）。
- 采购链验证：采购链节点只写 `in_transit_qty/pi_confirmed_unshipped_qty/po_unconfirmed_pi_qty`（阶段A已启用），且**不触发 /generate**；`suggested_qty` 仅在手动「重新计算」时重写。故 240 与采购链操作无关。
