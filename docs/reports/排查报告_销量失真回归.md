# 回归排查报告：销量失真 SKU 的特殊计算分支在 P4 被抹除

> 排查方式：只读。读 `server.js` 的 `detectStockoutDistortion` / `classifySkuState` / `generate` 主循环，比对「已提交基线」「P4 验收报告」与「当前真实库数据」。未改动任何代码。
> 结论：用户判断成立——**「销量失真」SKU 以前确实有单独分支（目标库存基数走「失真修正基准=断货前最高月销量」），P4 在「整链统一到销量统计周期口径」时把这段修正一起删掉了，且只删了基数修正、保留了标签/说明，导致现在失真 SKU 走普通公式被严重低估。**

---

## Q1. 以前「销量失真」SKU 是否真的有单独分支？—— 有

证据链（三处互相印证）：

1. **代码残留**：`server.js:1719` 的 `detectStockoutDistortion(m1,m2,m3,m4,available)` 是**完整的失真检测 + 修正基准返回函数**，注释明写「判断近期销量骤降是否由缺货导致，**返回修正基准销量**」，失真时 `adjustedAvg = maxSales`（4 个月最高月销量，即断货前峰值）。函数存在即说明历史上它被用于修正某个基数。
2. **注释自白**：`server.js:2137` 注释「目标库存计算（**P4**：基数改销量统计周期月均 `avg_sales_period`，**不再用缺货失真修正基准**）」—— 直接承认「以前用、P4 不用了」。
3. **验收报告旁证**：`P4_验收报告.md` 第 84 行：`RDM998STD`「基数因『失真修正被移除 + period 月均更低』从 ~17/20 落到 1.67/0」，并写明备份库（P4 前）该 SKU `suggested_qty=148`、当前=7。**148 正是用 4 月峰值（17/20）× 目标周转（≈4）算出**，证明旧公式失真渠道走峰值。

---

## Q2. 现在为什么走到普通公式？

`generate` 主循环里，`detectStockoutDistortion` **仍在调用且结果算出来了**，但**只用于贴标签，没用于算数**：

- `server.js:2134-2135`：照常算出 `onlineDist` / `offlineDist`（含 `adjustedAvg`）。
- `server.js:2137-2139`（**回归点**）：目标库存直接用原始 period 月均，完全没引用 `adjustedAvg`：
  ```js
  // 目标库存计算（P4：基数改销量统计周期月均 avg_sales_period，不再用缺货失真修正基准）
  const online_target_stock  = Math.round(online_avg_sales_period  * online_target_turnover);
  const offline_target_stock = Math.round(offline_avg_sales_period * offline_target_turnover);
  ```
- `server.js:2207-2212`：只把失真结果**追加到 risk_tags 和 sales_reason**（`push('销量失真')` + 说明文案），对 `suggested_qty` 无任何影响。

即：**检测还在、标签还在、文案还在，唯一被删的是「把修正基准代入基数」这一步。** 所以失真 SKU 现在和正常 SKU 走同一条 `period月均 × 目标周转`，而它的 period 月均恰被缺货压到极低 → 建议采购量被系统性低估。

## Q3. 是哪段后续改动把特殊分支带坏的？—— P4（口径统一）

- 改动位置：`server.js:2137-2139`（注释 + 两行公式）。
- 触发背景：P4 任务「整链统一到『销量统计周期（period）』口径」，把正常 SKU 的基数从 `avg_sales_4m`（4 月）切到 `avg_sales_period`（可配置 60/90/120 天）。这一步本只应动「正常基数」，但实现时**把失真修正（`adjustedAvg`）一并丢弃**——属于「统一口径时漏保留特殊分支」。
- 注意：这是**回归（regression）**，不是新需求。原特殊分支在 P4 前一直存在，`detectStockoutDistortion` 函数本身就是为它服务的。

---

## Q4. 三个公式对比

| 对象 | 目标库存基数（逐渠道） | 失真渠道示例 |
|---|---|---|
| **正常 SKU（当前）** | `online_target_stock = round(online_avg_sales_period × online_target_turnover)`；offline 同理；`total = 线上+线下+other`；再 `online_pct = 线上period / 总period`，`online_base = max(0, 线上target − round(pool×pct))`，`suggested_qty = round(线上base+线下base+other)`（拦截则 0） | — |
| **失真 SKU（当前，已坏）** | **与正常 SKU 完全相同**（adjustedAvg 被算出但忽略）→ period 月均被缺货压低 → 基数低估 | `RDM998STD`：线上 1.33×4=5、线下 0×4=0 → 合计 5（应≈148） |
| **失真 SKU（原本应走）** | 失真渠道用 `adjustedAvg`（=4 月峰值 `maxSales`）替代被压低的 period 月均，其余（正常渠道、分摊、拦截）不变：`base = isDistorted ? adjustedAvg : avg_sales_period` | `RDM998STD`：线上 17×4=68、线下 20×4=80 → 合计 148 ✅ |

**下游完全共用**：三类 SKU 在 `total_target_stock → 渠道分摊 → 业务拦截(shouldBlockReplenish) → suggested_qty → PUT/前端` 这一段路径完全一致，唯一差异只在「目标库存基数取哪个值」。因此修复只需改基数那一行。

## Q5. 最小修复方案（只恢复失真分支，不动正常逻辑）

### 改动点（仅 `server.js:2137-2139` 这一段，2 行改、2 行加）
`onlineDist` / `offlineDist` 已在 `server.js:2134-2135` 算好，可直接用：

```js
// 销量失真还原（P4 误删，本次仅恢复此分支）：
// 失真渠道用「断货前最高月销量(修正基准)」替代被缺货压低的 period 月均，避免补货量低估；正常渠道仍走 period 月均，不受影响。
const online_base_avg  = onlineDist.isDistorted  ? onlineDist.adjustedAvg  : online_avg_sales_period;
const offline_base_avg = offlineDist.isDistorted ? offlineDist.adjustedAvg : offline_avg_sales_period;
const online_target_stock  = Math.round(online_base_avg  * online_target_turnover);
const offline_target_stock = Math.round(offline_base_avg * offline_target_turnover);
```

### 明确「不动」的清单（守住已调顺的正常采购逻辑）
- `classifySkuState` 纯函数：不改（动销状态/风险标签/建议动作判定全不动）。
- 正常 SKU 公式：不改（`isDistorted=false` 时 `base_avg = avg_sales_period`，与现状逐字节一致）。
- 渠道分摊口径（online_pct 用 raw period 月均）：**本次保持不变**（最小改动原则；失真渠道 target 升高、分摊占比不变 → 其 base 自然更大，方向正确。若后续要连分摊也用修正基准，单独评估）。
- `shouldBlockReplenish` 拦截逻辑：不改（失真 SKU 的 sales_status=缺货/缺货风险，本就不在拦截清单内）。
- 生命周期系数 `LIFECYCLE_COEFF`：不改（见下方「观察」，本次范围外）。
- PUT 手动改建议采购端点：不改（pre-P4 也无失真分支，按既有架构只修 generate 主循环）。
- 前端 / 自动重算 / 三周转口径：不改。

### 验证清单
1. 取 3~5 个失真 SKU（如 `RDM998STD`/`RDBM4062`/`NAGA M730-RGB`）做「改前/改后」独立重算对比：
   - `RDM998STD` 改后 `suggested_qty` 应回到 ≈148（而非 5）；
   - `RDBM4062` 线上 target 应从 91 → ≈296；
   - `NAGA M730-RGB` 线上 target 应从 44 → ≈172。
2. 取 3 个**正常**（非失真）SKU 重算，确认 `target_stock` / `suggested_qty` **逐字节不变**（证明没动正常逻辑）。
3. `node --check server.js` 通过；服务重启后跑一次 `POST /api/replenishment-suggestions/generate`，确认 81 个失真 SKU 的建议采购量整体抬升、其余 0 矛盾。
4. 全量行数 / 顶部 KPI 中 `needReplenish`（需补货数）应上升，符合预期（之前被低估）。

### 回滚
- 把 `server.js:2137-2139` 改回 `round(avg_sales_period × target_turnover)` 两行即可，零副作用。
- 建议改前先 `cp data/inventory.db data/inventory.db.bak-distortion-fix-<时间戳>`。
