# 审批流管理 — 产品方案梳理（v0.1，仅方案，未改代码）

> 目标：把「审批 / 确认 / 抄送」三类动作理清，规划一个统一「审批流管理」页，覆盖采购、费用、运营、库存等板块。
> 本文只做产品梳理，不落地任何代码。文末列出待你拍板的决策点。

---

## 一、设计原则

| 类型 | 本质 | 是否阻塞主流程 | 适用场景 |
|---|---|---|---|
| **审批 Approval** | 有权的人「拍板能不能过」 | ✅ 阻塞式：不通过不能进入下一节点 | 涉及钱、对外承诺、合规 |
| **确认 Confirmation** | 责任人「已知会 + 承诺执行」 | ⚠️ 软阻塞/责任确认：卡其职责范围，不一定卡全链路 | 需要相关角色「知道并行动」，但业务合理性不由其批准 |
| **抄送 CC / Notify** | 纯知会 | ❌ 不阻塞 | 相关方需要「看到」，无需动作 |

核心区分：**审批 = 决定「能不能做」；确认 = 承诺「我会做」；抄送 = 只是「告诉你」**。

## 二、现有采购/费用节点的分类映射

（基于当前代码已有权限模型 `po_approve / payment_approve / check_approve / inbound_confirm / ci_edit` 等）

| 流程节点 | 当前实现 | 建议类型 | 理由 |
|---|---|---|---|
| PO draft → 提交 → 升 PI | 已有 `po_approve` + `/submit-approval` | **审批** | 采购金额、供应商、交期，必须有人批准 |
| 定金支付 | `payment_approve` | **审批** | 出钱 |
| 尾款支付 | `payment_approve` | **审批** | 出钱 |
| 关税 / 商检 / 到仓费 | `payment_approve` | **审批** | 出钱 |
| 库存调整单 | — | **审批/确认** | 调整影响库存账面，需确认合理性（建议按金额阈值：小额确认、大额审批） |
| 盘点差异 | `check_approve` | **审批** | 账实差异需批准 |
| 入库确认 inbound | `inbound_confirm` | **确认** | 仓库确认实际到货数量 |
| CI 费用确认完整 | `confirm-costs` | **确认** | 确认费用已补全 |
| **PI → CI/PL（出货）** | 当前无 | **确认 + 抄送** | 见第三节 |

## 三、重点：PI → CI/PL 不做「审批」，做「运营出货确认任务」

### 业务本质（你的判断）
这一步不是「批准发货」——发货由采购/物流决定。真正要的是：**电商运营必须知道这批货要出货了，并且提前规划上架，不能忘记做上架计划。**

所以它是一个**「确认任务」**，不是「审批」。

### 建议流程
1. **触发**：PI 状态进入「待 CI/PL」(`pending_ci_pl`) 或生成 CI 时，自动给**关联品牌的电商运营**创建一条「出货上架确认任务」。
2. **任务内容**
   - 知会：这批货的 SKU / 数量 / 预计出货日期 / 预计到仓日期。
   - 运营须确认/填写：**上架渠道、计划上架日期、是否需营销动作**。
   - 时限：例如出货前 N 天必须确认，超时升级提醒。
3. **阻塞策略（两种硬度，由你定）**
   - **软阻塞（推荐默认）**：不卡 CI 生成；但货到后若该批仍「未确认上架计划」，在库存/运营看板高亮预警，并抄送主管。
   - **硬阻塞**：CI 实际发货（或入库）前必须运营确认，否则不允许推进。
4. **抄送**：任务创建时抄送 运营主管 / 客服（备咨询）/ 财务（物流与关税预估）。

> 这样 PI→CI/PL 既不会被「审批」卡住正常发货节奏，又能保证运营不漏掉上架计划。

## 四、审批层级与抄送配置

- **审批层级（多级）**：`approvals` 表支持多层级（level 1/2/3…），不同对象可配不同层级。
  - 例：小额 PO 一级审批；大额 PO 二级（采购主管 + 财务）；特殊品牌三级。
  - 当前已有 `po_approve` 单级骨架，需扩展为「层级链」。
- **抄送规则**：`cc_rules` 表，按「节点 → 抄送角色/用户列表」配置，可固定也可自定义。
- **确认任务**：`confirmation_tasks` 表，含 节点 / 对象ID / 确认人(角色) / 状态(待确认/已确认/超时) / 时限 / 必填字段(上架计划等)。

### 三类落地的数据模型建议（仅示意，未建模）
```
approvals           节点, 对象ID, 审批人, 层级, 状态, 历史
confirmation_tasks  节点, 对象ID, 确认角色, 状态, 时限, 必填字段JSON
cc_rules            节点, 抄送角色/用户列表
```

## 五、与现有权限的衔接

- **审批**：复用 `po_approve` / `payment_approve` / `check_approve`。
- **确认**：复用 `inbound_confirm` / `ci_edit`；运营上架确认建议新增 `ops_listing_confirm`（或并入 `ci_edit` 职责）。
- **抄送**：无权限，仅通知（消息/站内信/邮件）。

## 六、统一「审批流管理」页构想

一个聚合页，按板块（采购 / 费用 / 运营 / 库存）归类，给当前用户展示：
- **待我审批**：所有阻塞式审批待办。
- **待我确认**：所有确认任务（含运营出货上架确认）。
- **我发起的**：审批/确认进度跟踪。
- **抄送我的**：已抄送、仅查看。

这样既统一管理，又避免每个列表页各自塞按钮导致入口分散。

## 七、待你拍板的决策点

1. **PI→CI/PL 运营确认**：要「软阻塞（预警）」还是「硬阻塞（卡发货）」？
2. **审批层级**：要不要多级？不同品牌/金额是否走不同层级？
3. **抄送**：固定角色，还是每节点可配置抄送人？
4. **统一页**：是否要做一个聚合「待我审批 / 待我确认 / 抄送我的」的审批流管理页？
5. **运营上架确认**：确认人按「品牌」归属（一个品牌一个运营），还是按「SKU/仓库」更细维度？
