# 方案：预测参数设置 × 当前筛选上下文自动关联

> 阶段：A-Step1 已通过（已去兜底、未命中阻止重算、来源切到 dim_default_config）。
> 本轮目标：把目标周转规则的维护入口，从「抽象自由规则表」改为「跟随当前筛选上下文直接配置」。
> **本文件为方案文档，未改动任何代码。**

## 结论先行（Q5：入口放哪里）

**保留在「销售 > 订单预测 > 预测参数设置」，不挪到系统管理页面。**

理由：
1. **业务流天然贴合**：你的操作路径是「筛选国家/仓库/品牌 → 看数据 → 发现未命中 → 补规则 → 重算」。补规则的决策点就在预测页面里，入口应放在痛点上。
2. **报错已指向这里**：当前未命中时弹出的 `showUnmatchedRules` 已写明「请在 ⚙ 预测参数设置 中为这些品牌添加规则」（app.js:3972），工作流已经这么接。
3. **筛选值就在手边**：预测页的 `rp-c / rp-w / rp-b` 三个下拉就是当前维度，预填零成本且 100% 准确，无需人工抄写长字符串（如 `Bekasi Warehouse`）。
4. **挪到系统管理会打断闭环**：到系统管理页要重新回忆/输入品牌+国家+仓库精确字符串，且脱离数据上下文，反而更易配错。

## Q1：预测参数设置能否直接读取当前筛选条件？

**能，且数据源可靠。**

当前筛选状态随时可从 DOM 读取（app.js:2838 `rpQuery()`、2845 `rpFilterBody()` 用的是同一来源）：

| 维度 | 元素 | 取值规则 |
|---|---|---|
| 国家 | `#rp-c` | 选中值；`全部` 项 `value=""` |
| 仓库 | `#rp-w` | 选中值；`全部` 项 `value=""` |
| 品牌 | `#rp-b` | 选中值；`全部` 项 `value=""` |

- 下拉项 `value` 与显示文本一致（如 `<option value="印度尼西亚">印度尼西亚</option>`），即 value 就是实际命中用的字符串。
- 默认筛选：国家=`印度尼西亚`(或`印尼`)、品牌=`Redragon`(若存在)、仓库=`全部`。打开弹窗时上下文默认即 `Redragon / 印度尼西亚 / 通配仓库`，已是合理起点。
- 结论：`openRpParams()` 启动时直接 `document.getElementById('rp-c/rp-w/rp-b').value` 即可拿到当前上下文，无需任何后端改动。

## Q2：打开弹窗后能否明确显示「正在配置哪一组维度」？

**能。** 在弹窗顶部加一条**上下文横幅（只读）**，三个维度用徽章展示，空白值显示「通配（全部）」：

```
┌──────────────────────────────────────────────────────────────┐
│  当前正在配置目标周转规则：                                      │
│  [品牌: Redragon]  [国家: 印度尼西亚]  [仓库: 通配（全部）]      │
└──────────────────────────────────────────────────────────────┘
```

- 非空白 → 显示实际值（蓝/绿徽章）。
- 空白（=全部）→ 显示「通配（全部）」（灰徽章），并在旁注一行：
  「通配 = 该维度不限，命中时作为更宽范围兜底」。
- 三种示例形态均可清晰呈现：
  - `Redragon / 印度尼西亚 / Bekasi Warehouse`（最具体）
  - `Redragon / 印度尼西亚 / 通配（全部）`
  - `Netac / 通配（全部） / 通配（全部）`

## Q3：保存时能否直接存成「当前维度」规则，而非维护自由表？

**能，且这正是本方案的核心变化。** 由「整表覆盖式自由表」改为「单条上下文 upsert」。

### 旧模式（要去掉）
`openRpParams` 渲染一整张 brand/country/warehouse/online/offline 自由表 + 新增规则按钮；`saveRpParams` 把整张表作为新的 `dim_default_config` 覆盖保存。用户需自己维护「一张抽象表」。

### 新模式（推荐）
1. 弹窗只展示 **当前上下文横幅 + 线上周转 / 线下周转 两个输入框**。
2. 输入框**预填该上下文已存在的规则值**（若存在）；不存在则预填「当前上下文中最佳命中规则的值」作参考起点（如品牌级已配 4，则填 4），并标注「当前无专属规则，以下为参考值」。
3. 点保存 → 前端**计算合并后的完整 `dim_default_config`**：
   - 读取现有 `dim_default_config`（GET `/api/system-config`）；
   - 按 key `brand|country|warehouse` **删除同键旧规则**（upsert 语义）；
   - **追加当前上下文新规则**（brand/country/warehouse 取筛选实值，空=通配）；
   - 其余规则原样保留。
4. POST 回 `/api/system-config`（后端无需改动，沿用现有通用保存接口）。

> 这样保存的始终是「当前这一组维度」的规则；其它维度规则不动，用户不再需要面对/维护整张抽象表。

### 可选增强（默认隐藏，避免回到自由表）
保留一个「⚙ 高级：手动添加其它维度规则」折叠区，复用旧自由行表格给高级用户应急（比如要配一个当前没筛到的维度）。**默认收起、非主路径**，不破坏「上下文驱动」主流程。

## Q4：「全部」如何映射成通配规则？

**`全部` 的 `value=""` 天然等于 dim_default_config 的「空=通配」约定，零转换。**

| 筛选选择 | 存入 dim 的值 | 含义 |
|---|---|---|
| 品牌=全部 | `brand=""` | 通配品牌 |
| 国家=全部 | `country=""` | 通配国家 |
| 仓库=全部 | `warehouse=""` | 通配仓库 |

按组合需注意两种边界，弹窗给**显式提醒**（不阻止，仅确认）：

1. **三处全为「全部」→ 全通配规则 `""/""/""`**
   - 评分 0，会作为最低优先级 catch-all 命中「所有未单独配置的 SKU」。
   - 由于已无兜底值，这条几乎等同于「全局默认」。**弹窗强提示**：「你正在配置『全通配』规则，将覆盖所有未单独配置的品牌/国家/仓库——这相当于全局兜底，确认需要吗？」（二次确认按钮）。
2. **品牌=全部、国家/仓库具体 → `""/国家/仓库`**
   - 会命中「该国家+仓库下的所有品牌」。合法（国家-仓库级默认），但跨品牌，弹窗提示「此规则将作用于该国家/仓库下的全部品牌」。

> 推荐主用法仍是「品牌具体 + 其它通配」（如 `Netac / 通配 / 通配`），与你举例一致。

## 改动范围（仅前端，后端不动 → 全部边界保持）

**改（app.js 内）：**
- `openRpParams()`：读取 `rp-c/rp-w/rp-b` 当前值 → 渲染上下文横幅；周转输入框预填当前上下文规则值；移除「整张自由表 + 新增规则」主路径（高级区折叠可选）。
- 新增 `currentRpContext()` 小工具：返回 `{brand,country,warehouse}` + 显示用解析（空→`通配（全部）`）。
- `saveRpParams()`：改为 upsert 语义——读现有 `dim_default_config` → 删同键 → 追加当前上下文规则 → 整体 POST；保留「周转必须正数」校验；全通配时弹二次确认。
- 可选：`addRpDimRow()` 仅保留给高级折叠区使用。

**不动（明确边界）：**
- server.js：`getDimTurnover` / `getDimTurnoverConfig` / generate 预检逻辑 —— 不变。
- P4 采购链（suggested_qty / 分摊 / 占比公式）—— 不变。
- `classifySkuState` / `risk_tags` / `shouldBlockReplenish` —— 不变。
- PUT / 系统管理页面结构 / 其它功能 —— 不变。
- 保存仍走现有 `POST /api/system-config`，后端零改动。

> 注：数据一致性提醒（非新风险，与现在 generate 预检同根）——warehouses 表的国家/仓库名须与 inventory/skus 实际值一致，否则 dim 命中仍会失败。本方案因直接取下拉值，反而比手工输入更不易出错。
