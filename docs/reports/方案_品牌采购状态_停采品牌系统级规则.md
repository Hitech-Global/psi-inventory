# 方案：品牌采购状态（停采品牌）沉淀为系统级规则

> 状态：方案稿（未改代码，待确认后实施）
> 目标：把"停止合作/不再采购品牌（如 BOYA）"从一次性特例，沉淀成品牌级的系统规则，联动订单预测。

---

## 一、当前实现现状（已核对代码）

| 关注点 | 现状 | 位置 |
|---|---|---|
| 品牌是否主数据 | 否。`/api/brands/all` 仅聚合去重字符串 | server.js:252 |
| 品牌设置页 | 只读：品牌名 + 关联 SKU 数，无状态、不可编辑 | app.js:561 `renderBrandSettings` |
| 停采能力 | 仅在 **SKU 级** `status='stopped'` 生效：预检跳过、generate 跳过、`sales_status='停采/停产'`、`action='停止采购，不参与补货'`、`suggestion='停采/停产，不参与补货建议'` | server.js:1966 / 1983 / 1748 / 1779 / 2211 |
| PO 候选过滤 | 已按 `suggested_qty > 0` 过滤 | app.js:4188 `genPOModal` |
| 去兜底预检 | 未命中 dim_default_config 的 SKU 会**阻止整页重算** | server.js:1962-1977 |

**结论**：品牌级"停采"目前完全没有。要做的是新增一个**品牌主数据 + 采购状态**层，并在 generate 链路里把"品牌停采"当作与"SKU 停采"同级的跳过/归零信号。

---

## 二、数据层（db.js，新增表 + 迁移）

新增品牌主数据表（不动任何现有表）：

```sql
CREATE TABLE IF NOT EXISTS brand_settings (
  brand TEXT PRIMARY KEY,
  procurement_status TEXT DEFAULT 'active',  -- 'active'=可采购 / 'stopped'=停采
  note TEXT DEFAULT '',
  updated_at TEXT DEFAULT ''
);
```

- 兼容升级：`CREATE TABLE IF NOT EXISTS` 幂等，旧库自动建表。
- 无记录 = 默认 `active`（不要求预填，零迁移成本）。
- 不新增任何现有表的列，不影响既有结构。

## 三、后端（server.js，新增 2 接口 + 改 generate 预检/循环）

### 3.1 新增接口

1. `GET /api/brand-settings`（`requireApiPermission('system_config')`）
   - 返回 `SELECT brand, procurement_status, note FROM brand_settings` 的全量数组。
   - 前端合并 `/api/brands/all` 的牌子，未在 brand_settings 中出现的一律视为 `active`。

2. `POST /api/brand-settings`（`requireApiPermission('system_config')`）
   - 入参 `{ items: [{ brand, procurement_status, note }] }`。
   - 逐条 `INSERT ... ON CONFLICT(brand) DO UPDATE` 写 procurement_status。
   - 仅改这两个字段，**不碰** dim_default_config / system_config 其它键。

3. 新增纯函数 `getBrandStatusMap()`
   - 一次 `SELECT brand, procurement_status FROM brand_settings`，返回 `{ [brand]: 'active'|'stopped' }`，供 generate 用 O(1) 查。

### 3.2 改 generate 预检（server.js:1962-1977）

- 在循环前 `const bstatus = getBrandStatusMap();`。
- 预检循环里，对每条待处理 SKU：
  ```js
  if (!skuPre || skuPre.status === 'stopped') continue;          // 既有 SKU 级跳过
  if ((bstatus[skuPre.brand] || 'active') === 'stopped') continue; // ★新增：品牌级跳过
  const hit = getDimTurnover(...);
  if (!hit) { ... 收集 unmatched ... }
  ```
- 效果：**停采品牌不要求命中 dim 规则，也不阻止整页重算**（直接命中你"去兜底"决策的预期：BOYA 这类已停采品牌不再因无规则而拦住全页）。

### 3.3 改 generate 循环（server.js:1980 起）

- 循环内新增品牌级判定：
  ```js
  const brandStopped = (bstatus[sku.brand] || 'active') === 'stopped';
  ```
- 若 `brandStopped`（且非 SKU 级 stopped，后者仍走既有 `return`）：
  - **不调用 getDimTurnover / 不要求命中**（避免 null 报错）。
  - `classifyTarget` 取一个中性值（如 dim 命中则用之、否则回退 3）仅供周转展示列，**不影响采购**。
  - 走正常计算后，**强制 `suggested_qty = 0`**（覆盖业务拦截后的结果）。
  - 在 `classifySkuState` 调用**之后**覆盖三个展示字段（不改纯函数本身）：
    - `sales_status = '停采/停产'`
    - `action = '停止采购，不参与补货'`（与现有 SKU-stopped 文案一致，保证全系统口径统一）
    - `suggestion = '品牌已停采，不参与补货建议，优先消化库存'`
  - `risk_tags` 保留 classifySkuState 原计算结果（高库存等仍作信息展示，与"清库存"动作不矛盾）。
  - 该行仍 **INSERT/UPDATE 进 replenishment_suggestions**（保持可见，见下方决策点 ⚠️）。

> 设计要点：**不改 `classifySkuState` 纯函数、不改 `shouldBlockReplenish`、不改 `getDimTurnover`**。品牌停采只是在 generate 循环里"后置覆盖"三个展示字段 + 强制归零，属最小侵入。

### 3.4 PO 候选（app.js:4188，无需改）

- `genPOModal` 已按 `suggested_qty > 0` 过滤 → 停采品牌 qty=0 自动不进 PO，**第④点天然满足**。
- （可选加固，非必须）后续若想更显式，可在过滤里加 `&& brandStatusMap[r.brand] !== 'stopped'`，但当前由 qty=0 已覆盖，本轮不做。

## 六、⚠️ 需你拍板的 3 个决策点

1. **停采品牌 SKU 在预测页是否保持可见**
   - 现状 SKU 级 `stopped` 是 `return`（重算后整行消失，预测页看不见）。
   - BOYA 你说了"还有库存在卖" → **建议改为：品牌停采的 SKU 仍写入 replenishment_suggestions（qty=0 + 停采标签），保持可见**，便于你看着清库存。
   - 这会与"SKU 级 stopped 直接消失"产生行为差异（品牌停采=可见清库存；SKU 停采=下架消失）。**是否接受这种差异？** 或你也想把 SKU 级 stopped 一并改成"可见 qty=0"？（后者超出本轮，需另说）

2. **文案口径**
   - 品牌停采复用 SKU-stopped 的 `action='停止采购，不参与补货'`，保持全系统一致。
   - 还是你想要更强调"清库存"的专属文案（如 `action='停止采购，优先消化库存'`）？方案默认用现有统一文案。

3. **BOYA 是否本轮直接预设为停采**
   - 最小做法：部署后你在品牌设置页手动把 BOYA 设为"停采"即可。
   - 或我在 db 迁移里顺带 `INSERT` BOYA=stopped（一次性）。**是否要我预设？**
