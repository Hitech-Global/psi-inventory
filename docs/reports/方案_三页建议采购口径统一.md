# 方案：订单预测三页「建议采购数量」口径统一（最小修复）

> 只读排查结论 + 最小修复方案。本轮**不改代码**，先确认方案。

## 0. 用户拍板的原则（硬性）
当 `other = 0` 时，必须满足：
**总预测建议采购 = 线上建议采购 + 线下建议采购**

不接受「总预测一套公式、线上/线下另一套公式」并存导致的三页不一致。

---

## 1. 根因确认（只读，已定位）

三页当前由**三处不同公式**分别计算，互不共享：

| 位置 | 公式 | 关键差异 |
|---|---|---|
| 后端 `suggested_qty` 列（generate，server.js:2224-2238） | `round(online_base + offline_base + other_final)`，拦截/品牌停采时整行=0 | 唯一会写库的值；**品牌停采时强制 0** |
| 前端线上/线下页（app.js:3183） | `max(0, targetStock − allocatedStock)`，乘 `_block` | **独立重算**；`_block=shouldBlockReplenish(r.sales_status,r.risk_tags)`，对「停采/清库存」返回 false → 品牌停采仍显示非零 |
| PUT 手动改（server.js:2367-2368） | `max(0, totalTarget − pool) × LIFECYCLE_COEFF` | 第 3 套公式，与 generate 的逐渠道分摊不同 |

### 三页不一致的直接原因
1. **品牌停采分叉（主因）**：后端把品牌停采 SKU 的 `suggested_qty` 置 0，但前端渠道页不拦截 `'停采/清库存'`，仍算出非零 → 总预测页=0、渠道页≠0。
2. **前端独立重算漂移**：渠道页用存储字段重算，与后端 generate 时刻的输入（拦截结果、停采覆盖）可能不一致。
3. **PUT 第三公式**：手动改 `target_stock` 后，后端用另一公式重算 `suggested_qty`，重新引入分叉。

> 注：两个 `shouldBlockReplenish`（server.js:1752 / app.js:2313）逻辑**完全相同**，拦截规则本身不是分叉源。

---

## 2. 最小修复方案：后端为唯一口径，按渠道拆分存储

### 2.1 统一采用哪一套公式（唯一口径）
**以后端 generate 的逐渠道分摊公式为唯一口径**；把每个渠道的「建议采购」单独算出来并**存库**，三页全部**读库值**，不再各自重算。

```
online_base  = max(0, online_target_stock  − round(total_inventory_pool × online_pct))
offline_base = max(0, offline_target_stock − round(total_inventory_pool × offline_pct))
other_final  = other_target_stock || 0
```
其中 `online_pct = online_avg_sales_period / avg_sales_period`（与前端 `pctPeriod` 完全一致，已核实）。

### 2.2 如何保证「总预测 = 线上 + 线下」（other=0 时）
后端在 generate 时把**每个渠道分量**算出并存储，且 `suggested_qty = 三分量之和`：

```
online_suggested_qty  = blocked||brandStopped ? 0 : round(online_base)
offline_suggested_qty = blocked||brandStopped ? 0 : round(offline_base)
other_suggested_qty   = blocked||brandStopped ? 0 : round(other_final)
suggested_qty         = online_suggested_qty + offline_suggested_qty + other_suggested_qty
```

三页读取：
- 总预测页：Σ `suggested_qty`
- 线上页：Σ `online_suggested_qty`
- 线下页：Σ `offline_suggested_qty`

由构造保证：`Σsuggested_qty = Σonline + Σoffline + Σother`；当 `other=0` 时，**总预测 = 线上 + 线下 严格成立**（整型相加，无取整误差，无拦截/停采不一致）。

### 2.3 需要改哪些文件 / 函数
**共 3 个文件，范围收敛：**

1. **db.js（加列）**
   - 在 `replenishment_suggestions` 增加 3 个可空整型列：`online_suggested_qty`、`offline_suggested_qty`、`other_suggested_qty`（初始化时幂等 `ALTER TABLE`，列已存在则跳过）。
   - 不动任何既有表/索引。

2. **server.js（两处）**
   - **generate 主循环**（约 server.js:2224-2238 + UPDATE 列清单 2278-2305 + INSERT 列清单 2306+）：
     - 把 `online_base/offline_base/other_final` 落为三个分量列；
     - `suggested_qty` 改为三分量之和（去掉原 `Math.round(online_base+offline_base+other_final)` 的整体 round，因分量已是整型，值不变）；
     - 拦截 / 品牌停采覆盖同时作用于三个分量（整行置 0）。
   - **PUT 端点**（server.js:2348-2391，手动改触发）：把 `suggested_qty` 重算改为「保持未改动的渠道分量不变、仅按改动后的 `target_stock` 重算对应分量，再求和」。即与 generate 同源，避免引入第 3 套公式。
     - `moq_qty` / `carton_adjusted_qty` 仍按整箱向上取整（基于 `suggested_qty` 之和），作为**独立展示列**，不计入三页「建议采购数量」合计（保证可加性精确）。

3. **app.js（渠道页只读库值）**
   - 渠道页计算段（约 app.js:3155-3183）：将 `r._c.suggestedQty` 由「前端重算」改为读取存储值：
     - 线上页：`r._c.suggestedQty = r.online_suggested_qty || 0`
     - 线下页：`r._c.suggestedQty = r.offline_suggested_qty || 0`
   - 保留 `allocatedStock` 计算（仅供「手动改建议采购」反推 `target_stock` 用，见 `onChannelTargetStockChange`，不动）。
   - 渠道页「建议采购数量」列的 `td`/`sum` 已用 `c.suggestedQty`，改源头即可，无需动渲染器。
   - 总预测页**不动**（已 Σ `r.suggested_qty`，符合新口径）。
   - 三周转显示 `afterOrderTurnover` 仍用 `c.suggestedQty`，改后自动一致。

### 2.4 对四大已调顺逻辑的影响（明确无影响）
| 已调顺逻辑 | 是否受影响 | 说明 |
|---|---|---|
| 停采品牌逻辑 | **否** | 品牌停采覆盖仍把 3 个分量 + `suggested_qty` 全置 0；SKU 仍可见、仍标注「停采/清库存」。本次修复只是让渠道页也显示 0（与总预测页一致），符合停采"优先清库存、不补货"本意 |
| 销量失真修复 | **否** | 失真分支只决定 `online_base/offline_base` 的基数（峰值修正），该基数继续作为 3 个分量与 `suggested_qty` 的输入，失真 SKU 仍按峰值算 |
| 多维目标周转 | **否** | `online_target_stock/offline_target_stock` 仍由 `getDimTurnover` 决定；分量由其派生 |
| 采购链 3 字段自动回写 | **否** | 回写的是 `in_transit_qty/pi_confirmed_unshipped_qty/po_unconfirmed_pi_qty`，与 `suggested_qty` 计算无关；`total_inventory_pool`（分配的输入）不受影响 |

## 3. 一处需你拍板的取舍（MOQ 是否进入「建议采购数量」列）
- **推荐（默认）**：三页「建议采购数量」= **原始整型分量之和（不含箱规取整）**，`moq_qty` 作为独立「整箱建议量」列展示，仅用于实际下单。这样可加性**精确成立**（无取整误差）。
- 备选：若希望展示列直接是整箱量，则对**每个分量**单独 `ceil(分量/箱规)×箱规` 后再求和——仍可加（分量各自取整后相加 = 总分量取整和），但数值比原始量大。
- 两种都不破坏「总=线上+线下」；区别仅在展示数字是否取整。**不影响本次修复目标**。
