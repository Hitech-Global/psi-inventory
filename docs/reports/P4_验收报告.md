## 1）公式链验收（3 个不同类型 SKU 完整对账）

通用公式（server.js generate，已逐行独立复核）：
- `online_target_stock = round(online_avg_sales_period × online_target_turnover)`
- `offline_target_stock = round(offline_avg_sales_period × offline_target_turnover)`
- `total_target_stock = online + offline + other_target_stock`
- `online_pct = online_avg_sales_period / avg_sales_period`
- `online_allocated = round(total_inventory_pool × online_pct)`（即「分摊总库存」线上部分）
- `online_base = max(0, online_target_stock − online_allocated)`；offline 同理
- `suggested_qty = round(online_base + offline_base + other_target_stock)`（拦截为 0 时直接置 0）

### A：占比不是 100% 的 SKU —— `NT02P500PRO-032G-S`（印度尼西亚 / Bekasi Warehouse）

| 字段 | 值 |
|---|---|
| avg_sales_period（总月均） | 185 |
| online_avg_sales_period / offline_avg_sales_period | 85 / 100 |
| 目标周转（online / offline） | 4 / 4 |
| 线上占比 | 85 ÷ 185 = **45.9%** |
| 总库存池（可用+在途+PI已确认未发+PO未确认） | 9 |
| 分摊总库存（线上） | round(9 × 45.9%) = **4**（线下=5） |
| online_target_stock / offline_target_stock | 340 / 400 |
| other_target_stock | 0 |
| total_target_stock | 740 |
| **suggested_qty（存储）** | **731** |
| 独立重算 suggested_qty | 336 + 395 + 0 = **731** ✅ 吻合 |

**为什么是 731**：该 SKU 几乎无库存（池仅 9），未触发任何拦截（sales_status=缺货风险，无风险标签），所以建议采购量≈目标库存 740，扣掉已有 9 即为 731。
**P4 前后对比**：备份库 suggested_qty = 547，当前 = 731。差异来源＝目标库存基数（4m 月均 139 → period 月均 185），占比几乎不变（4m 46% ≈ period 45.9%），所以幅度变化完全由基数切换解释。

### B：被拦截为 0 的 SKU

**例 1：`RDG711`（印度尼西亚 / Bekasi）**
| 字段 | 值 |
|---|---|
| sales_status | 新品/销售数据不足 |
| risk_tags | 高库存关注, **高库存严重** |
| shouldBlockReplenish | **true**（命中「高库存严重」） |
| total_target_stock / 总库存池 | 5 / 96 |
| **suggested_qty（存储）** | **0** |
| 独立重算 | 拦截强制 0 ✅ |

**例 2（决定性例子，证明拦截层真实生效而非顺带为 0）：`NT03US11C-032G-32BK`**
| 字段 | 值 |
|---|---|
| sales_status | 正常动销 |
| risk_tags | 高库存关注 |
| shouldBlockReplenish | **true**（命中「高库存关注」） |
| online_target_stock / 总库存池 / 线上分摊 | 21 / 15 / 15 |
| 若不拦截，online_base = max(0, 21−15) = **6** | 拦截后强制 **0** |

→ 该 SKU 若不被拦截本应建议采购 6，拦截层将其压为 0，证明 P4 没有误伤也确实保留了拦截逻辑。

### C：多渠道分摊变化明显的 SKU —— `RDM998STD`（印度尼西亚 / Bekasi）

| 字段 | 备份（P4 前，4m 口径） | 当前（P4 后，period 口径） |
|---|---|---|
| 总月均 | avg_sales_4m = 9.25 | avg_sales_period = 1.67 |
| online / offline 月均 | 4.25 / 5 | 1.67 / 0 |
| 线上占比 | 4.25 ÷ 9.25 = **45.9%** | 1.67 ÷ 1.67 = **100%** |
| online_target_stock / offline_target_stock | 68 / 80 | 7 / 0 |
| total_target_stock | 148 | 7 |
| 总库存池 | 0 | 0 |
| **suggested_qty（存储）** | **148** | **7** |
| 独立重算 | 68+80 = 148 ✅ | 7+0 = 7 ✅ |

**为什么是 7**：未拦截（sales_status=缺货，risk_tags=销量失真，均不触发拦截）。线上分摊=0、线上目标库存=7 → 线上 base=7；线下 period 近 90 天销量为 0 → 线下目标库存=0。合计 7。
**多渠道分摊变化点**：4m 口径下线下仍有过去 4 个月销量（offline_4m=5），占比 54.1%，贡献 offline_target_stock=80；切到 period 后线下近 90 天销量为 0，占比跌到 0%，整个线下渠道目标库存被抹掉（80→0），同时基数因「失真修正被移除 + period 月均更低」从 ~17/20 落到 1.67/0。即 **占比变 + 基数变两者叠加**，是本次最典型的「渠道分摊重构」样本。

## 4）PO 候选变化说明

PO 候选定义：复用既有规则 `suggested_qty > 0`（PO 生成过滤逻辑未改）。

| 指标 | 备份（P4 前） | 当前（P4 后） |
|---|---|---|
| PO 候选 SKU 数 | 130 | 131 |
| 候选状态翻转的 SKU 数（0 ↔ >0） | — | **13** |

**翻转原因拆解**（基于「各库自身存储的 target_stock」+「generate 实际使用的占比」独立重算；重算备份库 suggested_qty 与存储值 0 处不一致，sanity=0，证明口径还原正确）：

| 原因 | 数量 |
|---|---|
| 仅 target_stock 基数变（4m 失真修正 → period 原始） | 12 |
| 基数变 + 占比变（两者叠加） | 1 |
| 仅占比变（4m→period 分摊） | **0** |
| 其他 | 0 |

**结论**：
- PO 候选**集合**的变化几乎全部由「target_stock 基数切换」驱动（12/13）；仅 1 个 SKU 同时受占比变化影响。
- **占比（4m→period）单独没有让任何 SKU 跨过 0 边界**——但它显著改变了许多 SKU 的 suggested_qty 量级（最典型如第 1 节 C：`RDM998STD` 的线下渠道 80 件被抹掉）。即占比重构影响「建议采购多少」，基数切换影响「是否进入 PO 候选」。
