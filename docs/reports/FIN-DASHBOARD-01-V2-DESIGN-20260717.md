## 一、当前页面结构问题分析

当前实现（app.js:6557-6674 `renderCockpitView` / `renderCockpitDetails`；server.js:5752-5896 聚合端点）为"付款列表+统计页"形态，距"财务驾驶舱"定位存在 6 处偏差：

| # | 问题 | 位置 | 性质 |
|---|---|---|---|
| P1 | 顶部指标以**币种为第一视觉分层**：每个币种独立成块，块内重复 总应付/已结清/未结清/账龄，风险指标（已逾期/7天/30天）被埋在各币种块内，非第一眼可见 | app.js:6571-6583 | 经营风险视角缺失 |
| P2 | **"无到期日(未结清)"作为普通 KPI 卡**展示，与"已逾期"同等视觉权重；但其本质是**数据质量问题**（CI出货日/Credit未录入），非经营风险金额 | app.js:6581 | 业务KPI 与数据质量信号混淆 |
| P3 | **总应付/已结清占据顶部主位**：二者是"规模/构成"指标非"风险"指标，挤占风险视图的视觉优先级 | app.js:6575-6576 | 视觉优先级错配 |
| P4 | 供应商总览**缺"最近付款日期"**：当前有 未结清/已逾期/最早到期日/未结笔数，无法判断供应商付款活跃度/久未付款风险 | app.js:6601；server.js:5835-5853 | 风险视角不完整（用户明确要求补） |
| P5 | **应付明细默认全展开**（13列），首页过长，弱化"驾驶舱=风险汇总"定位 | app.js:6616-6619 | 信息密度过高 |
| P6 | **费用类型汇总位置偏前**（在供应商总览之前）：属"构成"视角非"风险"，干扰风险阅读顺序 | app.js:6586-6597 | 排序干扰 |

## 二、V2 页面布局方案

自上而下分层，第一视觉=经营风险，币种为辅（保留拆分但不作第一视觉，严守"不跨币种合计"）：

### Layer 0 — 标题/口径条（保留，精简）
- 标题「🧭 财务应付驾驶舱」+ 数据时间 + 今天日期
- 口径说明折叠为一行可展开提示（不占主视觉）

### Layer 1 — 经营风险主视图（第一视觉，6 卡）
| 卡 | 内容 | 币种处理 |
|---|---|---|
| ① USD 未结清 | 未结清金额 | 单币种 |
| ② RMB 未结清 | 未结清金额 | 单币种 |
| ③ 未来7天付款压力 | 到期日落入未来7天且未结清的金额 | 卡内按币种分列「USD xx ｜ RMB yy」，**不合并** |
| ④ 未来30天付款压力 | 到期日落入未来30天且未结清的金额 | 同上，按币种分列不合并 |
| ⑤ 已逾期 | 逾期未结清金额 + 逾期笔数 | 金额按币种分列副文本 |
| ⑥ 数据异常提醒 | **「XX笔付款缺少应付日期」**（alert 琥珀色样式），原因「CI出货日/Credit条件未完整录入」；点击→自动展开明细并过滤到无到期日行 | 按币种分列笔数副文本 |

> 说明：③④⑤ 因"不跨币种合计"冻结，卡内以「USD xx ｜ RMB yy」双行/副文本呈现，不输出单一合并数；既保风险优先又不违反冻结。

### Layer 2 — 金额构成（次要条，缩小）
- 总应付 / 已结清（按币种，小字次要条）——保留规模信息但不抢第一视觉
- 由 Layer 1 下方移至此处，视觉降级

### Layer 3 — 供应商付款风险总览（保留 + 强化）
列顺序（风险优先）：

| 列 | 来源 | 说明 |
|---|---|---|
| 供应商 | supplier_name | |
| 币种 | currency | |
| 未结清金额 | outstanding | 风险主指标 |
| 已逾期金额 | overdue_amount | 风险主指标 |
| 最早到期日 | earliest_due_date | 空=无到期日 |
| **最近付款日期** | **last_payment_date（新增只读派生）** | 识别久未付款 |
| 未结清笔数 | outstanding_count | |
| **风险标** | 前端派生（无新字段） | 有逾期=红 / 即将到期(30天内有且无逾期)=黄 / 正常=灰 |
| 下钻 | 复用 cockpitDrill | |

- 总应付/已结清列**降级**（灰显或可隐藏），突出风险列
- 默认排序：**已逾期金额降序 → 未结清降序**，高风险供应商置顶

### Layer 4 — 按费用类型汇总（下移）
- 保留，位置由"供应商总览之前"下移至"之后"；属构成视角，让位风险视角

### Layer 5 — 应付明细（默认折叠）
- 默认收起，首页仅显示折叠条：「应付明细（共 N 条，未结清 M 条）」+「展开查看」按钮
- 展开后呈现现有 13 列明细 + 仅看未结清/关键词过滤（保留）
- 无到期日行加「数据异常」小标，与 Layer 1 告警呼应
- 从 Layer 1「数据异常提醒」或 Layer 3 供应商「下钻」点击时，自动展开并应用过滤

## 四、是否需要新增接口字段

**仅需新增 1 个只读派生字段**（不涉及任何禁止项）：

### `by_supplier[].last_payment_date`（最近付款日期）

- **原因**：用户要求的供应商付款风险视角需"最近付款日期"识别久未付款供应商；当前 `by_supplier` 无此字段（server.js:5835-5853）。
- **数据来源（已验证可支持，复用已算好的派生值）**：`paymentSettlementFacts` 已内置 `facts.latestPayment`（server.js:4923-4926，按 `paid_date`/`created_at` 排序取最新 `status='applied'` 的付款事件）。后端在 enriched 行暴露 `last_payment_date = facts.latestPayment?.paid_date || pr.paid_date || ''`，再在 `by_supplier` 聚合时取 MAX（字符串日期比较）。
- **无 logs 回退**：`paymentSettlementFacts` 在无 payment logs 时 `effectivePaid` 回退 `paid_amount`（server.js:4912-4914）；对应地 `last_payment_date` 回退 `payment_requests.paid_date`（legacy 列），保证空库也有值。
- **性质**：只读派生展示字段。**不新增业务规则、不改 `paymentSettlementFacts` 计算逻辑（仅读取其已产出的 `latestPayment`）、不改状态机/汇率/WAC、不改表结构、不改付款链**。仅在后端聚合端点内追加一个字段计算 + 前端渲染一列。
- **当前数据现状**：隔离副本 `payment_settlement_logs` 为空（已结清金额来自 `paid_amount` 回退），故 `last_payment_date` 将回退到 `payment_requests.paid_date`；待真实付款事件落库后自动取 `logs.paid_date`。

**其他字段：无需新增。**
- 风险标 = 前端派生（基于已有 overdue_amount/due_soon/earliest_due_date）
- 7天/30天压力的币种分列 = 前端按已有 `metrics[cur].due_7/due_30` 渲染
- 其余均为已有字段的重排/重样式
