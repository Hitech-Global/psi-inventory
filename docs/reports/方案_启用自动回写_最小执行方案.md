# 方案：启用采购链 → 库存总表自动回写（最小执行方案 / 阶段 A）

> 范围：仅「启用自动回写」，不动自动重算挂载、不动三周转口径统一。
> 目标：采购链状态变化能自动回写库存总表的 4 个字段——
> `po_unconfirmed_pi_qty` / `pi_confirmed_unshipped_qty` / `in_transit_qty` / `available_qty`。

---

## 0. 现状回顾（已读代码确认的事实）

两个函数的**本体逻辑完整正确**，仅首行 `return;` 被禁用：

| 函数 | 位置 | 当前状态 | 本体逻辑 |
|---|---|---|---|
| `updateInventoryTransitData()` | server.js:937 | `return;` 禁用（L939） | **全量重算**：按 `sku_code+country+warehouse` 聚合 CI/PI/PO 单据，把 3 个在途字段 SET 成计算值（非 `+=`） |
| `updateInventoryAfterInbound(...)` | server.js:3364 | `return;` 禁用（L3366） | **增量**：`available_qty = available_qty + qty`（仅入库时 +） |

两函数的**调用点原本就存在**，只是被 `return` 跳过：

| 调用点 | 位置 | 触发节点 | 调用内容 |
|---|---|---|---|
| 库存导入后 | 932 | 导入 | `updateInventoryTransitData()` |
| PI 创建后 | 2700 | PI 创建 | `updateInventoryTransitData()` |
| CI 创建后 | 2837 | 发货（CI） | `updateInventoryTransitData()` |
| 单条入库后 | 3148 | 入库（单条） | `updateInventoryTransitData()` |
| 批量入库后 | 3250 | 入库（批量） | `updateInventoryTransitData()` |
| 批量入库内 | 3227 | 入库（批量） | `updateInventoryAfterInbound()` ← **仅批量有，单条漏调** |

## 1. 需要改哪些文件 / 函数

**仅改 `server.js`，不动 `db.js` / `app.js` / 前端 / generate 公式。**

### 必做
1. **server.js:939** 删除 `return;`（启用 `updateInventoryTransitData`）。
2. **server.js:3366** 删除 `return;`（启用 `updateInventoryAfterInbound`）。
3. **单条入库 POST（~3107）补调用**：当前单条入库只调了 `updateInventoryTransitData`(3148)，**漏调** `updateInventoryAfterInbound`。需在入库成功后补 `updateInventoryAfterInbound(d.sku_code, d.country, d.warehouse, d.actual_qty, d.inbound_date)`。
4. **PO 创建（~2484）补调用**：新建 PO 写入 `po_qty`、`transferred_pi_qty=0`，但当前**不触发** `updateInventoryTransitData` → 新 PO 不会进 `po_unconfirmed_pi_qty`，直到第一次建 PI 才被顺带重算。建议在 PO 创建事务提交后补 `updateInventoryTransitData()`。
5. **PI 批量导入（~2902，transferred_pi 更新在 ~2935）补调用**：该 handler 更新 `transferred_pi_qty` / `pi_confirmed_qty` 但**不触发** `updateInventoryTransitData` → 批量建 PI 不刷新在途字段。建议补 `updateInventoryTransitData()`。
6. **`updateInventoryAfterInbound` 内加重防重保护**（详见第 4 节）：按 `inbound_no` 查重，已存在则跳过 INSERT 与增量。

### 可选（建议补齐，成本低）
7. **取消 / 状态变更端点补调用**：`updateInventoryTransitData` 的 SQL 已对 `cancelled` 状态过滤（`po/pi/ci_status NOT IN ('cancelled',...)`），但当前代码里没看到把 PO/PI/CI 置为 `cancelled` 的显式端点。若存在取消入口，应在状态变更后补 `updateInventoryTransitData()`，使被取消单据不再贡献在途量。

## 2. 各节点回写字段映射（PO / PI / 发货 / CI / 入库）

> 说明：本系统中「发货」= **CI 创建**（CI 即商业发票=发货单据，`shipped_qty` 在 CI 创建时写入，PI 明细 `shipped_qty` 同步累加）。没有独立于 CI 的「发货」端点。故下表「发货」与「CI」合并为一行。

| 节点 | 代码触发点 | 调用函数 | 回写字段 | 说明 |
|---|---|---|---|---|
| **PO 创建** | 2484 | `updateInventoryTransitData()`（需补） | `po_unconfirmed_pi_qty`（其余两字段全量重算） | `po_qty` 写入、`transferred_pi_qty=0` → 全额进 `po_unconfirmed_pi_qty` |
| **PI 创建** | 2700 | `updateInventoryTransitData()` | `pi_confirmed_unshipped_qty`↑、`in_transit_qty`（经 shipped 间接） | `pi_confirmed_qty` 写入、`shipped_qty=0` |
| **PI 批量导入** | 2902/2935 | `updateInventoryTransitData()`（需补） | 同上 | 当前漏触发 |
| **发货 / CI 创建** | 2837 | `updateInventoryTransitData()` | `pi_confirmed_unshipped_qty`↓（随 shipped 增长）、`in_transit_qty`↑ | `shipped_qty` 写入 → 在途出现 |
| **入库（单条）** | 3107→3148 | `updateInventoryTransitData()` + `updateInventoryAfterInbound()`（需补） | `in_transit_qty`↓、`available_qty`↑ | 当前单条**漏调** afterInbound |
| **入库（批量）** | 3156 | `updateInventoryAfterInbound()` + `updateInventoryTransitData()` | `available_qty`↑、`in_transit_qty`↓ | 已完整 |

关键点：`updateInventoryTransitData()` 是**全量重算**，任一节点触发都会把**全库**相关 3 字段刷新到正确值。因此「漏掉的节点」只影响**及时性**，不影响**最终正确性**——下一次任意采购操作都会把它补算回来。

---

## 3. 哪些状态变化会触发回写

**会触发（启用后即生效）：**
- PO 创建 / PO 转 PI（`transferred_pi_qty` 变化）
- PI 创建 / PI 发货（`pi_confirmed_qty`、`shipped_qty` 变化）
- CI 创建 = 发货（`shipped_qty` 写入）
- 入库（单条 / 批量）（`inbound_qty` 增长 → 在途下降；`available_qty` 增长）

**不会触发 / 需补（见第 1 节）：**
- PO 创建当前不触发（必补）
- PI 批量导入当前不触发（必补）
- 取消类（`cancelled`）：SQL 已支持过滤，但需确认是否存在取消入口并补触发（可选）

---

## 4. 如何避免重复累加 / 重复扣减

### 4.1 `updateInventoryTransitData()` —— 天然安全
- 它是**全量重算**：`UPDATE inventory SET xxx = 计算值`，不是 `+=`。
- 无论被调用多少次、在哪个节点调用，结果都等于「按当前单据实时聚合」，**不会重复累加**，也**不会重复扣减**。
- 结论：**此函数无需任何防重处理，放心启用。**

### 4.2 `updateInventoryAfterInbound()` —— 必须防重（增量 `+=`）
- 风险：`available_qty += qty` 是增量。若同一笔入库被处理两次（同 `inbound_no` 重复提交、或同一文件重复批量导入），`available_qty` 会被**重复 +**。
- 另外注意：入库明细 `commercial_invoice_items.inbound_qty` 也是增量累计（L3213/3215 `accumulated = old + actualQty`），重复导入同样会重复累计 → 进一步放大错误。
- **防护（必做）**：
  1. 在 `updateInventoryAfterInbound` 内（或调用前）按 `inbound_no` 查重：若已存在同 `inbound_no` 的入库记录，则**跳过 INSERT 与 `+=`**。
  2. 批量导入逐行做同样查重（同一文件重复导入应整行跳过，且不重复累计 CI 的 `inbound_qty`）。
- **扣减不在此函数范围**：出库扣减由 outbound 模块独立处理（现有 L1038/1171/4642 等 `available_qty - qty`），与入库 `+` 是两条独立流水，不会重复扣。

### 4.3 ⚠️ 关键决策点 D1：`available_qty` 的归属冲突
- 当前 `available_qty` 由**库存导入**以「覆盖」方式维护（L924 `available_qty = ?`）。
- 启用 `updateInventoryAfterInbound` 后，入库会对其做 **`+=`**。
- 冲突场景：导入一份「已包含某批到货」的快照后，之前那批入库的 `+=` 仍留在库里 → **重复计数**。
- 这与「阶段 A 只启用回写、不改主链」的 Minimal 目标有张力，需在确认方案时拍板（见第 6 节 D1）。

---

## 5. 对现有订单预测主链是否有影响

- `generate` 读取这 4 个字段计算**总库存池**与**三周转**（server.js:2086-2089，存库 L2276）：
  `总库存池 = available_qty + in_transit_qty + pi_confirmed_unshipped_qty + po_unconfirmed_pi_qty`。
- 启用回写后：**采购链变更 → 4 字段即时反映真实状态 → 用户下次点「重新计算」时，池/周转自动正确**（不再需要先手动导入在途快照）。
- **本步骤不触发 `generate`**（自动重算留待后续议题）→ 字段即时更新，但 `replenishment_suggestions` 仍要手动重算才刷新，与现状一致。
- **不影响现有手动导入流程**：导入仍覆盖 `available_qty`；导入后 L932 仍会重算 3 个在途字段。
- 不影响 brand_settings / 停采逻辑 / 维度命中 / PUT 手动改建议采购等任何既有逻辑。

---

## 6. 这一步是否仍然不改 generate 公式本体

**是。本步骤只改「库存总表 4 字段的写入时机」，完全不碰：**
- `generate` 公式本体 / `classifySkuState` / 建议采购数量算法
- 前端任何代码
- 自动重算挂载、三周转口径统一（按计划留待后续单独决定）

## 7. 决策点（确认方案时需拍板）

**D1. `available_qty` 归属冲突（最重要）**
- 选项 A（最稳，推荐作为本步默认）：本步**先只启用 3 个在途字段**（`updateInventoryTransitData`），`available_qty` 的入库 `+=` **暂不开启**，避免与导入覆盖冲突。这样「采购链状态自动回写」已覆盖 3/4 字段且无任何风险，等 `available_qty` 归属规则定下再开第 4 个。
- 选项 B：启用 `available_qty +=`，但明确规则「重新导入库存快照会把 `available_qty` 重置为该快照值（吸收历史入库增量）」，并在 UI/文档提示；接受「导入截至日之前」的入库不重复、「导入截至日之后」的入库正确累加。
- 选项 C（改动更大）：导入只作初值播种，日常 `available_qty` 由「入库 + 出库」流水驱动（需改导入逻辑）。

**D2. 是否一并补齐 PO 创建 / PI 批量导入 / 取消端点的触发**
- 建议补齐 PO 创建与 PI 批量导入（必做项 4、5）；取消端点需先确认系统里是否已有取消入口。

**D3. `updateInventoryTransitData` 仅更新已存在的 inventory 行**
- 新采购 SKU 若还没有 inventory 行（未做过库存导入），其 transit 字段不会被写入（函数对 `if(inv)` 才更新）。属已知限制，可接受；若需覆盖，可改为「不存在则 INSERT 一行仅填 transit 字段」。

## 9. 风险与回滚

- **回滚极简**：把两个 `return;` 加回即可恢复「不自动回写」，零副作用。
- **改前备份**：按惯例先备份 `data/inventory.db`。
- **双重保险**：本步骤不触发生成，任何错误只影响 inventory 的 4 字段，可随时用导入 / 手动重算校正，不会污染 `replenishment_suggestions`。
