# 采购链（PO / PI / CI）与订单预测联动影响清单

> 文档性质：**只读梳理**，不改代码。基于 `server.js` / `db.js` / `app.js` 当前实现核对。
> 用途：在切入「采购链板块测试与优化」前，先把采购链各节点与订单预测页面的字段联动关系、状态流转、口径边界、以及「当前是否已自动联动」说清楚。

---

## 0. 阅读前必读：当前架构的三个核心事实

这三条决定了本清单里大量「联动」目前**并未真正发生**，而是靠人工维护：

1. **在途字段回写被禁用**。`server.js` 的 `updateInventoryTransitData()`（约 937-939 行）函数体第一行就是 `return;`，后面的计算逻辑被整体跳过。
   结果：`inventory` 表的 `in_transit_qty` / `pi_confirmed_unshipped_qty` / `po_unconfirmed_pi_qty` **不会**由 PO/PI/CI 单据自动算出，只能靠**库存导入**时人工填列。
2. **入库回写可用库存被禁用**。`server.js` 的 `updateInventoryAfterInbound()`（约 3364-3366 行）同样第一行 `return;`。
   结果：CI 入库**不会**自动增加 `available_qty`，可用库存同样只来自库存导入。
3. **没有任何采购动作触发预测重算**。订单预测数据只由用户手动点「重新计算」（`POST /api/replenishment-suggestions/generate`，约 1961 行）生成。PO/PI/CI/入库/库存导入**都不会**自动调用它。

> 结论：**今天的「联动」本质是「人工同步」**——用户导入一份含可用+在途+PI未发+PO未确认字段的库存快照，再点重新计算。下面清单会把每个节点标成三类状态：
> - **[手动]**：当前必须靠人工导入/重算才生效
> - **[禁用-可启用]**：代码已写好但被 `return` 禁用，启用即自动联动
> - **[模型]**：预测计算层本就按此公式处理，只差上游字段被填入

## 1. 状态流转定义

### 1.1 PO（采购订单）
| 状态 | 触发动作 | 对采购链自身的含义 |
|---|---|---|
| `draft` | 创建 PO | 草稿，未提交 |
| `pending_approval` | 提交审批 | 等待审批 |
| `approved` | 最终审批通过 | 已批准 |
| `sent_factory` | 标记已发工厂 | 已下发工厂 |
| `partial_pi` | 从该 PO 生成了部分 PI | 部分数量已转 PI |
| `transferred_pi` | 该 PO 全部数量已转 PI | 全部转 PI 完成 |
| `cancelled` | 取消 | 作废 |

- 关键数量：`purchase_order_items.transferred_pi_qty`（已转 PI 数量）在生成 PI 时累加（约 2678-2680 行）。
- 概念映射：`po_unconfirmed_pi_qty`（库存侧）= `po_qty − transferred_pi_qty`。

### 1.2 PI（形式发票）
| 状态 | 触发动作 | 含义 |
|---|---|---|
| `pending` | 创建 PI | 待处理 |
| `uploaded` | 上传附件 | 已传附件 |
| `shipped_complete` | 全部已发货（CI 发货后推导） | PI 货量已发完 |
| `completed` | 全部完成 | 终结 |
| `cancelled` | 取消 | 作废 |

- 关键数量：`proforma_invoice_items.pi_confirmed_qty`（PI 确认数量，创建时填列）、`shipped_qty`（CI 发货时累加，约 2795-2798 行）。
- 概念映射：`pi_confirmed_unshipped_qty`（库存侧）= `pi_confirmed_qty − shipped_qty`。

### 1.3 CI（商业发票 / 发货）
| 状态 | 触发动作 | 含义 |
|---|---|---|
| `draft` | 创建 CI | 草稿 |
| `uploaded` | 上传附件 | 已传附件 |
| `ci_pl_uploaded` | 上传 PL | 已传装箱单 |
| `partial_inbound` | 部分到货入库 | 部分已入 |
| `completed` | 全部到货入库 | 全部已入 |
| `cancelled` | 取消 | 作废 |

- 关键数量：`commercial_invoice_items.shipped_qty`（创建 CI 时填列）、`inbound_qty`（入库时累加）。
- 概念映射：`in_transit_qty`（库存侧）= `shipped_qty − inbound_qty`。

### 1.4 入库（Inbound）
- `inbound_records.inbound_status`：`completed`（正常）/ `abnormal`（异常）。
- 入库更新 `commercial_invoice_items.inbound_qty`，并据全部明细是否到齐推导 CI 状态为 `partial_inbound` / `completed`（约 3137-3143 行）。
- **[禁用]** 本应顺带增加 `available_qty`（见 0.2），当前不执行。

## 2. 字段映射总表（采购链 → 库存总表 → 订单预测）

| 采购链动作 | 写入的采购单字段 | 应映射到的库存字段 | 进入订单预测的字段 |
|---|---|---|---|
| 创建/审批 PO | `po_qty`、`transferred_pi_qty` | `po_unconfirmed_pi_qty` | 总库存池、建议采购数量 |
| 生成 PI | `pi_confirmed_qty`、`transferred_pi_qty`↑ | `pi_confirmed_unshipped_qty`（↑时 `po_unconfirmed_pi_qty`↓） | 总库存池、建议采购数量 |
| CI 发货 | `shipped_qty`（PI/CI） | `in_transit_qty`（↑时 `pi_confirmed_unshipped_qty`↓） | 总库存池、**在途后周转**、建议采购数量 |
| CI 入库 | `inbound_qty` | `available_qty`（↑时 `in_transit_qty`↓）**[禁用]** | **当前可用周转**、总库存池、建议采购数量 |

> **关键不变量**：同一批实物在「PO未确认 → PI未发 → 在途 → 可用」四个阶段间流转时，**总库存池总额基本不变**（只是组成比例在四个分量间迁移）。这是预期的正确行为——避免同一批货被重复计入。

---

## 3. 各节点联动影响（按你列的 1~4 点）

### 3.1 PO 创建 / 审批后
- **影响字段**：`po_unconfirmed_pi_qty`（= 全部 po_qty，因为还没转 PI）。
- **进池**：是 → 总库存池 ↑ → `建议采购数量 = max(0, 目标库存 − 池)` ↓（因为池变大了）。
- **三周转**：不直接变（PO未确认不参与 在途后/下单后 公式的分子，见第 4 节口径）。
- **当前状态**：**[禁用-可启用]** 需 `updateInventoryTransitData()` 启用；今天靠人工导入填 `po_unconfirmed_pi_qty`。
- **对预测页**：PO 创建本身**不会**让建议采购立即下降——必须等字段被填入 + 重新计算。

### 3.2 PI 确认 / 生成后
- **影响字段**：`pi_confirmed_unshipped_qty` ↑（= pi_confirmed_qty），同时 `po_unconfirmed_pi_qty` ↓（transferred_pi_qty 累加）。
- **进池**：池总量基本不变（PI未发 替代 PO未确认，同批货）。`建议采购数量` 基本不变。
- **三周转**：不变（PI未发不在 在途后 分子里）。
- **当前状态**：**[禁用-可启用]**；今天靠人工导入。

### 3.3 发货 / 在途后
- **影响字段**：`in_transit_qty` ↑（shipped − inbound），`pi_confirmed_unshipped_qty` ↓。
- **进池**：池总量基本不变（在途 替代 PI未发）。
- **三周转**：
  - **在途后周转 = (可用 + 在途) / 月均** → 因「在途」↑、**在途后周转 ↑**（更接近目标）。
  - **下单后周转** 也随在途 ↑ 而 ↑。
  - 当前可用周转 不变（可用没变）。
- **当前状态**：**[禁用-可启用]**；今天靠人工导入 `in_transit_qty`。

### 3.4 CI / 入库后
- **影响字段**：`available_qty` ↑（到货），`in_transit_qty` ↓（同批货离开在途）。
- **进池**：池总量**不变**（可用↑ 抵消 在途↓）——这是模型设计（见第 4 节）。
- **三周转**：
  - **当前可用周转 = 可用 / 月均** → ↑（可用变多）。
  - **在途后周转 = (可用+在途)/月均** → 不变（两者之和不变）。
  - **下单后周转** → 不变（池不变 → 建议采购不变）。
- **当前状态**：**[禁用]** `updateInventoryAfterInbound()` 被禁用，`available_qty` 仅靠人工导入。

## 4. 总库存池 与 三周转 的口径（重要边界）

### 4.1 总库存池（驱动建议采购数量）
```
总库存池 = available_qty + in_transit_qty + pi_confirmed_unshipped_qty + po_unconfirmed_pi_qty
```
**四个分量全部进池**（约 2091 行）。`建议采购数量 = max(0, 目标库存 − 总库存池)`。

### 4.2 三周转（前端实时公式，约 app.js 3194-3198）
| 指标 | 公式（前端 period 口径） | 分子包含 |
|---|---|---|
| 当前可用周转 | 可用库存 / 月均销量 | 仅 `available_qty` |
| 在途后周转 | (可用 + 在途) / 月均销量 | `available_qty` + `in_transit_qty` |
| 下单后周转 | (可用 + 在途 + 建议采购) / 月均销量 | `available_qty` + `in_transit_qty` + `建议采购数量` |

> ⚠️ **刻意的设计差异（务必注意）**：
> - **总库存池**把 PI未发、PO未确认 也计入（4 个分量）→ 影响 `建议采购数量`。
> - **三周转列**只算「可用 + 在途」（2 个分量）→ **不含** PI未发、PO未确认。
> - 含义：建议采购数量会「预扣」整条采购管道（含PI/PO阶段），但页面上「在途后周转 / 下单后周转」只反映到「在途」这一层，不会把 PI未发/PO未确认 算进周转。
> - 这造成一个**展示与建议的不一致**：你从建议采购看，PI未发/PO未确认 已被当成「已承诺库存」扣减；但你从在途后/下单后周转看，它们又没被算进去。后续优化采购链联动时，这是第一个要拍板的点（见第 9 节）。

### 4.3 另一处口径差异（仅说明，非 bug）
- DB 存量字段 `current_turnover_months` 用的是 **4 个月**口径（`pool / avg_sales_4m`，约 2125 行），前端三周转列用的是 **销量统计周期（period）**口径。前端不展示 DB 该字段，两者不同是预期（已写入项目记忆澄清）。

## 5. 哪些节点会影响「建议采购数量」

`建议采购数量 = max(0, 目标库存 − 总库存池)`，所以总库存池任一分量变化都会影响它：

| 节点 | 对池的影响 | 对建议采购的影响 | 当前是否自动 |
|---|---|---|---|
| PO 创建 | `po_unconfirmed_pi_qty` ↑ | ↓（池变大） | [禁用] 靠导入 |
| PI 生成 | 池组成迁移，总量≈不变 | ≈不变 | [禁用] 靠导入 |
| CI 发货 | 池组成迁移，总量≈不变 | ≈不变 | [禁用] 靠导入 |
| CI 入库 | 池总量不变 | 不变（但可用↑会拉低后续重算的缺口，若目标周转使得目标库存固定则建议采购不变） | [禁用] 靠导入 |
| 库存导入 | 四个分量整体刷新 | 按新池重算 | [手动] 需重新计算 |
| 改目标周转 / 销量统计周期 | 改「目标库存」与「月均」 | 直接改建议采购 | [手动] 需重新计算 |

> **要点**：建议采购数量只在**重新计算**时才重算；任何采购节点（即使启用了自动回写）如果不触发重算，预测页上的建议采购仍是旧值。

## 6. 哪些节点会影响 三周转

| 节点 | 当前可用周转 | 在途后周转 | 下单后周转 | 当前是否自动 |
|---|---|---|---|---|
| PO 创建 | — | — | — | [禁用] |
| PI 生成 | — | — | — | [禁用] |
| CI 发货 | — | ↑（在途↑） | ↑ | [禁用] |
| CI 入库 | ↑（可用↑） | —（可用+在途不变） | — | [禁用] |
| 改月均销量 | 随月均变 | 随月均变 | 随月均变 | [手动] 需重算 |

> 说明：「—」表示按当前公式该节点不改变该指标。三周转是前端 period 公式**实时算**，但分子读的是 `replenishment_suggestions` 里存好的 `available_qty`/`in_transit_qty`/`建议采购数量`，而这些存储值只在重新计算时刷新。

## 7. 自动重算 vs 仅刷新展示 矩阵

| 触发动作 | 是否改库存字段 | 预测页是否自动变 | 需要什么才生效 |
|---|---|---|---|
| PO 创建/审批 | 否（除非启用回写） | 否 | 启用回写 + 重新计算 |
| PI 生成 | 否（除非启用回写） | 否 | 启用回写 + 重新计算 |
| CI 发货 | 否（除非启用回写） | 否 | 启用回写 + 重新计算 |
| CI 入库 | 否（回写禁用） | 否 | 启用回写 + 重新计算 |
| 库存导入 | 是（导入即写 inventory） | 否（预测页读的是 suggestions 快照） | **重新计算** |
| 改预测参数（周转/周期） | 否 | 否 | **重新计算** |
| 手动点「重新计算」 | 触发全量 regenerate | 是 | — |

> **结论**：当前无论哪种采购动作，**预测页都不会自动刷新**，都必须点「重新计算」。即使将来启用 `updateInventoryTransitData` / `updateInventoryAfterInbound` 自动回写库存字段，预测页上的「建议采购/三周转」仍要重新计算才刷新（除非再额外把 generate 接到这些事件上）。

## 8. 当前实现红线（优化前必须知道）

- ✅ 订单预测读取的 `inventory.*` 在途字段，目前**只来自库存导入**，与 PO/PI/CI 单据**无自动关联**。
- ✅ `updateInventoryTransitData()`、`updateInventoryAfterInbound()` 两函数代码完整、逻辑正确，仅被 `return` 禁用——启用即可自动联动，无需重写算法。
- ✅ 生成 PO（从预测建议「生成PO」）**不会**立刻降低该 SKU 的建议采购；降低只发生在「库存字段被更新 + 重新计算」之后。这是预期（避免 PO 还没真正采购就提前清零建议）。
- ⚠️ 三周转（前端）与总库存池（建议采购）对 PI未发/PO未确认 的**口径不一致**（见 4.2），是后续联动优化的首要设计决策点。
- ⚠️ 没有任何采购/入库/导入动作挂载 `/generate`，重算完全手动。

## 9. 给后续采购链优化的待决策点（仅列，不动代码）

1. **是否启用自动回写**：把 `updateInventoryTransitData()` / `updateInventoryAfterInbound()` 的 `return` 去掉，让 PO/PI/CI/入库自动刷新 `inventory` 的在途与可用字段。
2. **是否在采购节点自动触发重算**：启用回写后，是否还要在 CI 入库 / PI 生成等关键节点自动调一次 `/generate`（或仅刷新展示），避免用户忘点「重新计算」。
3. **三周转口径统一**：是否把「PI未发 / PO未确认」也纳入在途后/下单后周转的分子（与总库存池一致），还是维持现状（只算可用+在途）。这是展示与建议一致性的核心取舍。
4. **入库即减在途的边界**：CI 入库时 `available_qty`↑ 且 `in_transit_qty`↓，按当前公式池总量不变——是否接受这种「入库不改变建议采购、只改变当前可用周转」的行为，还是要改成「入库即视为可用、池随可用上升而上升」（取决于是否把在途移出池）。
5. **PO 生成后建议采购的即时反馈**：是否要在「从预测生成 PO」后，把对应建议采购标记为「已下单/冻结」，让页面即时反映「已采购在途」，而不必等库存导入+重算。
6. **停采品牌联动**：品牌停采（上一轮已落地）目前只在 generate 时后置覆盖；若启用自动回写，停采品牌的在途/PI/PO 字段是否仍参与池计算（目前是参与的，只是最终 qty 被强制 0）。
