## 第一部分：销量统计周期 / 目标周转 — 多维默认值现状

### 1.1 当前参数设置页保存的到底是什么

**结论：保存的纯粹是全局参数，与你在预测页筛了什么品牌/国家/仓库完全无关。**

证据链：
- 前端 `openRpParams()`（app.js L3964-3997）：从 `/api/system-config` 读取全局值，弹窗只有 3 个字段（销量统计周期、线上目标周转、线下目标周转），**没有任何品牌/国家/仓库选择器**。
- 前端 `saveRpParams()`（app.js L3998-4015）：构造 3 个 config 对象 `{key, value}`，POST 到 `/api/system-config`。**payload 里不含任何维度信息**。
- 后端路由（server.js L553-565）：`POST /api/system-config` 收到 `configs` 数组，逐条 `INSERT ... ON CONFLICT(key) DO UPDATE`，**按 key 覆写全局值**。key 就是 `sales_stats_days` / `online_target_turnover_default` / `offline_target_turnover_default`，没有维度维度。
- generate 路由（server.js L1893, L1906-1908）：接收 `country/warehouse/brand` 参数，但这**只用于筛选本次处理哪些库存行**，所有被处理的 SKU 用的是**同一套全局参数**。

所以：你在预测页筛了"Netac / 印尼尼西亚 / Bekasi"再打开"预测参数设置"保存，改的仍然是全局的 `sales_stats_days=90`、`online_target_turnover_default=4`，**不会**存成"Netac 印尼尼西亚 Bekasi 专用默认值"。

### 1.2 system_config / 代码里已有哪些多维支持

**现状：只有"品牌"一个维度有部分支持，国家/仓库维度完全没有。**

system_config 表当前全部相关 key（实测）：

| key | 值 | 维度 | 用途 |
|---|---|---|---|
| `brand_target_stock_months` | `{"Redragon":4,"Netac":2,"__default__":3}` | **品牌级** | 品牌目标周转月数 |
| `sales_stats_days` | `90` | 全局 | 销量统计周期 |
| `online_target_turnover_default` | `4` | 全局 | 线上目标周转 |
| `offline_target_turnover_default` | `4` | 全局 | 线下目标周转 |
| `target_stock_months` | `4` | 全局 | 旧字段，generate 已不直接用（被 brand_target 取代） |
| `lead_time_months` | `2` | 全局 | 交货周期 |
| `stagnant_dead_days` | `180` | 全局 | 旧呆滞分级（见第二部分） |
| `stagnant_heavy_days` | `90` | 全局 | 同上 |
| `stagnant_medium_days` | `60` | 全局 | 同上 |
| `stagnant_light_days` | `30` | 全局 | 同上 |

代码中已有的多维取用逻辑：
- `loadBrandTargetConfig()`（server.js L1585-1591）：读 `brand_target_stock_months` JSON。
- `getBrandTargetMonths(brand, skuTargetTurnover, cfg)`（server.js L1595-1604）：优先级 = SKU手动 > 品牌默认 > `__default__`(3)。

### 1.3 目标周转真实取用链 — 品牌默认为什么被全局覆盖

这是你说的"品牌默认被全局默认覆盖"问题的精确根因：

```
generate 主循环 (server.js L2030-2033):
  online_target_turnover  = onlineDefault  > 0 ? onlineDefault  : brand_target_months
  offline_target_turnover = offlineDefault > 0 ? offlineDefault : brand_target_months
```

- `onlineDefault` = `online_target_turnover_default`（全局，当前=4）
- 当前全局 online=4、offline=4，**都 > 0**，所以 `brand_target_months` 分支**永远走不到**。
- 实测：Netac 在 `brand_target_stock_months` 配了 2，但实际用的是全局 4。

完整优先级（当前代码实际执行顺序）：
```
1. online_target_turnover_default / offline_target_turnover_default（全局，>0 就用它）
2. → 否则才回退 brand_target_months（品牌级）
   2a. inventory.target_turnover_months（SKU手动，当前全是0，且你不想要这层）
   2b. brand_target_stock_months[品牌]（品牌配置）
   2c. brand_target_stock_months.__default__（默认3）
```

另外实测 `inventory.target_turnover_months` 全部 396 行都是 0 → getBrandTargetMonths 第1层（SKU手动）从不命中。

### 1.4 用户需求与现状差距

| 用户需求 | 现状 | 差距 |
|---|---|---|
| 销量统计周期按 品牌/国家/仓库 设默认 | 全局单一值 `sales_stats_days=90` | **完全不支持**多维 |
| 目标周转按 品牌/国家/仓库 设默认 | 只有品牌级 JSON，且被全局值覆盖 | 品牌级有但被覆盖；国家/仓库完全不支持 |
| 不要 SKU 单独目标周转 | `inventory.target_turnover_months` 字段存在，getBrandTargetMonths 第1层检查它 | 字段在但全为0；需移除取用层 |
| SKU 层只接受手动改建议采购数量 | 已支持（渠道页编辑→PUT 反算） | 已满足 |

### 1.5 多维默认值方案设计（不改代码，仅方案）

#### A. 命中优先级设计

推荐优先级（从高到低）：

```
品牌+国家+仓库 > 品牌+国家 > 品牌 > __default__
```

不设"国家+仓库"或"国家"单维度组合（你的业务是品牌驱动，国家/仓库是品牌下的细分，跨品牌的国家级默认意义不大）。如果你认为需要国家级，可扩展为：

```
品牌+国家+仓库 > 品牌+国家 > 品牌 > 国家 > __default__
```

> 需要你确认：是否需要"国家"或"仓库"作为独立维度（脱离品牌），还是只在品牌下细分？

#### B. 配置结构设计

方案一（推荐）：JSON 嵌套，沿用 `brand_target_stock_months` 风格，新增两个 key：

```json
// key: brand_region_stats_days
{
  "Redragon": { "default": 90, "印度尼西亚": 90, "印度尼西亚|Bekasi Warehouse": 120 },
  "Netac": { "default": 60 },
  "__default__": 90
}

// key: brand_region_target_turnover
{
  "Redragon": { "default": { "online": 4, "offline": 4 }, "印度尼西亚": { "online": 5, "offline": 3 } },
  "Netac": { "default": { "online": 2, "offline": 2 } },
  "__default__": { "online": 3, "offline": 3 }
}
```

优点：单 key 存一棵树，前端弹窗可渲染为可编辑列表；命中时按 `品牌 → 品牌+国家 → 品牌+国家+仓库` 逐层降级查找。

方案二：扁平 key，每条配置一行（如 `target_turnover:Redragon:印度尼西亚:Bekasi Warehouse`），存 system_config 多行。优点是粒度清晰，缺点是前端编辑和命中查询都要拼 key、遍历全表。

## 第二部分：慢销 / 呆滞 / 高库存 / 高库龄 — 完整判断链

### 2.1 三套独立判断系统并存（重要前提）

当前代码里有**三套互不关联**的库存动销判断系统：

| 系统 | 函数/位置 | 用途 | 口径 | 是否被采购链使用 |
|---|---|---|---|---|
| **统一判断层** | `classifySkuState` (L1694) + `shouldBlockReplenish` (L1680) | sales_status / risk_tags / 补货拦截 | **4m 口径**（avg_sales_4m） | ✅ 是（generate + PUT） |
| **旧呆滞分析接口** | `/api/stagnant-analysis` (L3956) | stagnant_level 分级 | daysSinceSale（距上次销售天数） | ❌ 否（独立报表页） |
| **库存自动状态** | `recalcInventoryForSku` (L4220) | inventory.inventory_status | 写死90天月均 | ❌ 否（库存表字段） |

> 用户问的"慢销/呆滞/高库存/高库龄"主要落在**第一套（统一判断层）**，因为这套驱动补货拦截。第二、三套是独立报表/字段，不影响采购。

### 2.2 统一判断层 classifySkuState — 完整规则清单

> 位置：server.js L1694-1756。纯函数，输入 `o`，不查库。口径用 `avg_sales_4m`（近4个月月均），target = `brand_target_months`。

#### A. sales_status 判断（互斥，按顺序先命中先返回）

| # | 状态 | 判断条件 | 代码行 | 阈值来源 |
|---|---|---|---|---|
| 1 | 清仓 | `lifecycle_status === 'clearance'` | L1710-1711 | lifecycle 字段 |
| 2 | 停采/停产 | `lifecycle_status === 'stopped'` | L1712-1713 | lifecycle 字段 |
| 3 | 新品/销售数据不足 | 未过新品保护期（`!passedProtection`） | L1714-1715 | `new_product_protection_days`（skus表，默认90） |
| 4 | 无有效销售 | 已过保护期 且 `total_sales_ever === 0` | L1716-1717 | 历史总销量 |
| 5 | 缺货 | `available <= 0` | L1718-1719 | 可用库存 |
| 6 | 缺货风险 | `available > 0 && avg > 0 && availTurnover < 0.5` | L1720-1721, L1703 | **写死 0.5 个月** |
| 7 | 呆滞 | `sales_30d === 0 && available > 0 && passedProtection` | L1722-1723 | **写死 30 天**（L2001，不用 sales_stats_days） |
| 8 | 慢销 | `sales_90d > 0 && availTurnover > target × 2 && passedProtection && !stockoutRisk` | L1724-1725 | **写死 系数2 + 90天**（L2002，不用 sales_stats_days） |
| 9 | 正常动销 | 以上都不命中 | L1726-1727 | — |

其中：
- `availTurnover = available / avg_sales_4m`（L1700），avg>0 才计算，否则 null
- `sales_30d` = 近30天有效销量（L2001-2003，**写死30天，与 sales_stats_days 无关**）
- `sales_90d` = 近90天有效销量（L2002-2004，**写死90天**）

#### B. risk_tags 风险标签（并行判断，非互斥）

> 缺货/缺货风险时**抑制**高库存/高库龄标签（L1732 守卫），避免销量被缺货压低→周转虚高→误判高库存。

| 标签 | 判断条件 | 代码行 | 阈值来源 | 触发拦截？ |
|---|---|---|---|---|
| 高库存关注 | `availTurnover > target × 1.5` | L1733 | **写死 系数1.5** | ✅ 是 |
| 高库存严重 | `availTurnover > target × 2` | L1734 | **写死 系数2** | ✅ 是 |
| 高库龄风险 | `daysSinceInbound > 180 && available > 0 && availTurnover > target × 2` | L1735-1737 | **写死 180天 + 系数2** | ✅ 是 |
| 库龄未知 | 无入库日期 `!hasInboundDate` | L1739 | last_inbound_date 缺失 | ❌ 否 |
| 销量失真 | generate 主循环追加：`onlineDist.isDistorted \|\| offlineDist.isDistorted` | L2110-2114 | detectStockoutDistortion | ❌ 否 |
| 新品无销量 | generate 追加：`sales_status=新品/销售数据不足 && sales_30d=0 && sales_90d=0` | L2117-2118 | 写死 30/90天 | ✅ 是 |

#### C. shouldBlockReplenish — 补货拦截规则（L1680-1686）

```
拦截（suggested_qty = 0）当且仅当：
  sales_status ∈ {清仓, 停采/停产, 无有效销售, 呆滞, 慢销}
  或 risk_tags 含 {高库存严重, 高库存关注, 高库龄风险, 新品无销量}
```

注意：**高库存关注** 也拦截（L1683），不只是高库存严重。

### 2.4 哪些适合改成"品牌/国家/仓库"维度配置

| 阈值 | 是否适合多维配置 | 理由 |
|---|---|---|
| 慢销周转系数（×2） | ✅ 适合 | 不同品牌/市场的销售节奏不同 |
| 高库存关注系数（×1.5） | ✅ 适合 | 同上 |
| 高库存严重系数（×2） | ✅ 适合 | 同上 |
| 呆滞判断天数（30天） | ⚠️ 可选 | 30天是行业通用值，但某些市场（如印尼）物流周期长，可能需要 45/60 天 |
| 慢销判断天数（90天） | ⚠️ 可选 | 同上 |
| 高库龄天数（180天） | ⚠️ 可选 | 海运仓 vs 本地仓差异大 |
| 缺货风险阈值（0.5月） | ⚠️ 可选 | 交货周期长的市场可调高 |
| 新品保护期天数 | ✅ 适合 | 不同品牌新品策略不同（目前是 SKU 级，可加品牌级默认） |
| 生命周期系数 | ❌ 不建议 | 业务语义固定，跨品牌不应变 |

### 2.5 不建议配置化的

| 项目 | 理由 |
|---|---|
| 生命周期系数 LIFECYCLE_COEFF | 这是生命周期阶段→补货强度的业务映射，语义固定，配置化反而增加误配风险 |
| 判断顺序（生命周期→缺货→呆滞→慢销→高库存） | 这是业务逻辑骨架，不应可配 |
| 缺货/缺货风险抑制高库存标签 | 失真防护逻辑，不应可配 |
| shouldBlockReplenish 的拦截状态列表 | 业务安全规则，不应可配 |

### 2.6 统一判断层与多维默认值的关系

如果第一部分的"目标周转多维默认值"落地，classifySkuState 的 `target_months` 会自动跟着变（因为它接收的是 `brand_target_months`，而 brand_target_months 来自多维命中）。所以**多维目标周转落地后，慢销/高库存的判断基数会自动按维度区分**，无需额外改 classifySkuState。

但 classifySkuState 当前用 **4m 口径**（avg_sales_4m），如果后续 P4a 把分类层也切 period，则需同步把 L1698 `avg = o.avg_sales_4m` 改为 `o.avg_sales_period`，并确认 sales_30d/sales_90d 是否也要跟着 period 走（当前写死30/90天）。
